## 1. Résumé de la slice

`5-1` construit **la file de téléchargement et les six choix de masse de B18**. Elle prend
un roman, transforme le choix du lecteur en une liste ordonnée de `queue_items`, puis
drainne cette liste **un chapitre à la fois, dans l'ordre de lecture**. C'est la slice qui
rend SC-2 possible — cinquante chapitres téléchargés puis lus hors ligne — parce que
télécharger cinquante chapitres à la main ne démontre pas une file.

Trois choses qu'elle **ne** fait **pas**, chacune attribuée :

| Ce qui n'est pas ici | Où |
|---|---|
| Écrire le `.md` sur le disque | `2-3` (`ChapterStore.store`) |
| Pause / reprise / annulation | `5-2` |
| Progression, perte de connexion, stockage saturé | `5-3` |

La règle structurante est **B18** : *un par un, dans l'ordre de lecture*. La file est donc
**séquentielle par construction**, et `architecture.md` § 4.5 l'a dit en supprimant la
colonne de concurrence — une constante exprimée en colonne est une constante qu'une
implémentation pourrait changer. Il existe un test qui vérifie son absence
(`the queue has no concurrency column to mis-set`) : **ne pas la rajouter**, y compris
« juste pour mesurer plus tard ». Le besoin éventuel d'une colonne de concurrence est un piège
à écrire en § 7, pas un changement de schéma à faire.

**User stories couvertes** : US-07 (Télécharger un roman comme une file), US-06 (télécharger
un chapitre)

**Règles métier couvertes** : B18, B19 (la moitié structurelle ; voir § 6.1)
**Edge cases couverts** : E14, E15 (tracés, voir § 6.2)

```dart
// lib/core/database/app_database.dart — déjà implémenté, ne pas modifier
enum DownloadState { queued, downloading, done, failed }

class DownloadStateConverter extends TypeConverter<DownloadState, String> {
  const DownloadStateConverter();
  @override
  DownloadState fromSql(String fromDb) => DownloadState.values.byName(fromDb);
  @override
  String toSql(DownloadState value) => value.name;
}

@DataClassName('QueueRow')
@TableIndex(name: 'idx_queue_state', columns: {#state})
class QueueItems extends Table {
  TextColumn get id => text()();
  TextColumn get chapterId =>
      text().references(Chapters, #id, onDelete: KeyAction.cascade)();
  TextColumn get state => text()
      .map(const DownloadStateConverter())
      .withDefault(const Constant('queued'))();
  IntColumn get queuePosition => integer()();
  DateTimeColumn get addedAt => dateTime()();
  DateTimeColumn get startedAt => dateTime().nullable()();
  DateTimeColumn get finishedAt => dateTime().nullable()();
  IntColumn get attempts => integer().withDefault(const Constant(0))();
  TextColumn get errorCode =>
      text().nullable().withDefault(const Constant(''))();
  @override
  Set<Column> get primaryKey => {id};
}
```

**Le commentaire de `DownloadState` dans ce fichier est la spécification de B19 pour cette
slice** : *« `queued` and `downloading` are deliberately distinct: B19 lets the reader pause
a queue, and a paused item is `queued` with the queue stopped, not a fourth state.
Collapsing them would make "paused" unrepresentable. »* Donc **ne pas ajouter un état
`paused`**, et ne pas le déduire de `queuePosition`.

```dart
// lib/domain/downloads/bulk_choice.dart
/// Les six choix de B18, et rien d'autre.
///
/// **Il n'y a pas de septième choix**, et en particulier pas de
/// « tout, chapitres déjà lus compris » : `architecture.md` § 4.5 ne dit pas
/// « next N », le PRD le dit. Le seul moyen d'atteindre un chapitre déjà lu est
/// `HandPicked`, ce qui est précisément « selected by hand ».
sealed class BulkChoice {
  const BulkChoice();
}

/// « Le chapitre suivant » — le premier chapitre non stocké, quel que soit son
/// `isRead`. Voir § 3.1 pour pourquoi ce choix ne filtre pas sur `isRead`.
final class NextChapter extends BulkChoice {
  const NextChapter();
}

/// « Les 5, 10 ou 25 prochains » — [count] vaut 5, 10 ou 25, et rien d'autre.
final class NextChapters extends BulkChoice {
  const NextChapters(this.count) : assert(count == 5 || count == 10 || count == 25);
  final int count;
}

/// « Tous les chapitres non ouverts » — le seul choix qui filtre sur `isRead`.
final class AllUnopened extends BulkChoice {
  const AllUnopened();
}

/// « Les chapitres que vous choisissez » — l'ordre donné est l'ordre de la file.
final class HandPicked extends BulkChoice {
  HandPicked(this.chapterIds) : assert(chapterIds.length > 0);
  final List<String> chapterIds;
}
```

```dart
// lib/domain/downloads/bulk_choice_resolver.dart
/// La seule information qu'un choix a besoin sur un chapitre. Volontairement
/// **pas** un `ChapterRow` drift : le résolveur est une fonction pure, et une
/// fonction pure se teste sans base de données (`10-testing.md` règle 4).
final class DownloadableChapter {
  const DownloadableChapter({
    required this.id,
    required this.ordinal,
    required this.isRead,
    required this.downloadedAt,
  });

  final String id;

  /// L'ordre du site (B9). **Jamais** `number`.
  final int ordinal;
  final bool isRead;
  final DateTime? downloadedAt;

  bool get isStored => downloadedAt != null;
}

/// Renvoie les identifiants de chapitres à mettre en file, **dans l'ordre de la
/// file**. Fonction pure : aucune E/S, aucun provider, aucune base.
List<String> resolveBulkChoice(
  BulkChoice choice, {
  required List<DownloadableChapter> chapters,
}) {
  // ⚠️ L'ordre de lecture EST l'ordre de la file. On trie par `ordinal`, jamais
  // par `number` : `number` vaut -1 quand il est illisible et repart à chaque
  // volume, donc trier par là réordonne les volumes (2-3 § 3.3).
  final byReadingOrder = [...chapters]..sort((a, b) => a.ordinal.compareTo(b.ordinal));

  return switch (choice) {
    // Un chapitre déjà stocké n'est jamais remis en file
    // (07-downloads-offline.md règle 3 : « do not refetch »).
    NextChapter() => [
      for (final c in byReadingOrder)
        if (!c.isStored) c.id,
    ].take(1).toList(growable: false),

    NextChapters(:final count) => [
      for (final c in byReadingOrder)
        if (!c.isStored) c.id,
    ].take(count).toList(growable: false),

    // Le seul choix qui parle de lecture. `isRead == false` ET non stocké.
    AllUnopened() => [
      for (final c in byReadingOrder)
        if (!c.isRead && !c.isStored) c.id,
    ],

    // ⚠️ L'ordre est celui de la liste reçue, pas celui de `chapters` :
    // B18 veut « un ensemble choisi à la main », et `novel-details.md` § 11.3
    // dit qu'il n'y a **aucun geste de réordonnancement** dans la barre de
    // sélection. L'ordre du lecteur EST donc l'ordre d'insertion.
    HandPicked(:final chapterIds) => chapterIds
        .where((id) => chapters.firstWhere((c) => c.id == id).isStored == false)
        .toList(growable: false),
  };
}
```

```dart
// lib/domain/downloads/download_queue_repository.dart
import 'package:lumen_tale/core/database/app_database.dart';
import 'package:lumen_tale/domain/downloads/queue_entry.dart';

/// L'interface de la file. Implémentée par `data/repositories/drift_download_queue_repository.dart`.
///
/// **Aucune méthode de cette interface n'écrit `chapters.downloadedAt`.** La marque est
/// écrite par `2-3`, après le rename atomique (ADR-022), et par rien d'autre — voir § 3.4.
abstract interface class DownloadQueueRepository {
  /// La file entière, réactive. Alimentée par un `Stream` drift, pas par un rafraîchissement
  /// manuel (`05-state-management.md` règle 4).
  Stream<List<QueueEntry>> watchQueue();

  /// Les chapitres encore à faire, dans l'ordre de la file.
  ///
  /// **ORDER BY queue_position ASC** — c'est `queuePosition`, pas `chapters.ordinal`, que
  /// la file lit, parce qu'un ordre choisi à la main doit être honoré
  /// (`architecture.md` § 4.5). Un index existe sur `state`
  /// (`idx_queue_state`) et sert au filtre « en pause / en file ».
  Future<List<QueueEntry>> pending();

  /// Ajoute [chapterIds] dans l'ordre reçu, à partir de [firstPosition].
  ///
  /// Renvoie les lignes réellement insérées : un chapitre déjà en file est ignoré
  /// et n'est pas dupliqué. Voir § 3.2 pour les six branches.
  Future<List<QueueEntry>> enqueue(List<String> chapterIds, {int? firstPosition});

  /// `queued` → `downloading`, `attempts += 1`, `startedAt = now`.
  /// Un chapitre déjà `downloading` est renvoyé tel quel **sans** incrémenter
  /// `attempts` — voir § 3.3.
  Future<QueueEntry> markDownloading(String queueItemId);

  /// `downloading` → `done`, `finishedAt = now`, `errorCode = ''`.
  Future<void> markDone(String queueItemId);

  /// `downloading` → `failed`, `finishedAt = now`, `errorCode = <code>`.
  /// Le `state = failed` **n'efface pas** `downloadedAt` : un chapitre déjà stocké ne
  /// repasse pas par ici, donc il n'y a rien à effacer, et un chapitre jamais
  /// stocké n'a rien à effacer non plus.
  Future<void> markFailed(String queueItemId, String errorCode);

  /// Retire de la file toute ligne non `done`. Utilisé par `5-2` (annulation) et
  /// par « clear failed list ». **Ne touche jamais `chapters`.**
  Future<int> clearUnfinished();
}
```

```dart
/// L'interface de la boucle qui draine la file. Elle ne connaît **rien** de la
```

### 2.3 Contrats API

**Aucun appel d'écriture réseau propre à cette slice.** La boucle consomme la chaîne
existante, dont les trois appels sont ceux du contrat `Source` — et ils renvoient tous
`BrowseOutcome<T>`, jamais une liste nue, jamais `null` (B22, SC-6) :

```dart
// Le contrat tel que la file le consomme — signature, pas implémentation.
Future<BrowseOutcome<String>> fetchChapterContent(Chapter chapter);   // 2-1 / 6-1
Future<BrowseOutcome<List<Chapter>>> getChapterList(Novel novel);      // 2-1 / 6-1
```

Puis, dans cet ordre et **pas un autre** :

```
fetchChapterContent  →  BrowseOutcome<String>        (HTML brut)
   → BrowseSucceeded  →  2-2 nettoie et convertit    → Markdown
   → BrowseEmpty      →  5-1 : échec, errorCode = source_empty      (§ 3.3)
   → BrowseFailed     →  5-1 : échec, errorCode = <reason.name>    (§ 3.3)
Markdown → 2-3 ChapterStore.store()  →  fichier, PUIS downloadedAt   (ADR-022)
```

## 3. Algorithmes critiques

### 3.1 Résolution des six choix (couvre **B18**) — chaque branche écrite

La fonction est `resolveBulkChoice` (§ 2.2). Voici ses six entrées et ce qu'elles
renvoient, y compris **les cas vides**, qui sont la moitié du contrat.

| Choix | Condition | Entrée | Sortie | Pourquoi c'est correct |
|---|---|---|---|---|
| `NextChapter` | ≥ 1 chapitre non stocké | 100 chapitres, 12 stockés | **1** id, le premier non stocké en `ordinal` | B18 « the next chapter ». Le choix **ne filtre pas** sur `isRead` : `novel-details.md` § 11.1 dit que *Next chapter* reste disponible sur un roman dont tous les chapitres ont été ouverts, ce qui n'aurait pas de sens si le choix exigeait `isRead == false` |
| `NextChapter` | 0 chapitre non stocké | tout stocké | **liste vide** | La feuille reste ouverte et dit qu'il n'y a plus rien à télécharger ; aucune erreur, aucun dialogue |
| `NextChapters(5)` | 3 non stockés | | **3**, pas 5 | Le compte affiché par la feuille est **calculé par la même fonction** que celui enfilé — jamais un `min(5, total)` écrit à part dans le widget |
| `NextChapters(10)` / `(25)` | ≥ [count] non stockés | | **[count]** | idem |
| `NextChapters(n)` avec `n ∉ {5,10,25}` | — | — | **`AssertionError` au construction** | `assert` dans le constructeur de `NextChapters`. Un choix qui n'est pas dans B18 ne doit pas pouvoir exister |
| `AllUnopened` | 40 non ouverts dont 6 déjà stockés | | **34** | `isRead == false` **et** non stocké. Un chapitre ouvert puis téléchargé n'est pas re-téléchargé (règle 3 de `07-downloads-offline.md`) |
| `AllUnopened` | 0 non ouverts | | **liste vide** | Le roman peut être lu en ligne sans rien télécharger ; ce n'est pas une erreur |
| `HandPicked` | 3 ids, dont 1 déjà stocké | | **2**, dans l'ordre reçu | Règle 3 : pas de refetch. L'ordre reçu **est** l'ordre de la file |
| `HandPicked(ids)` vide | — | — | **`AssertionError`** | Une sélection vide n'est pas un choix, c'est un appui raté |
| `HandPicked(ids)` contenant un id inconnu | — | | **`firstWhere` échoue** | **Inatteignable par l'interface** : la barre de sélection ne propose que des ids qu'elle a affichés, et `novel-details.md` § 11.3 lui interdit d'en inventer. Le résolveur **documente** ce contrat dans une assertion et ne l'attrape pas — un id inconnu est un **défaut de appelant**, pas une entrée de recherche, et `13-error-handling.md` règle 1 veut une exception typée si quelqu'un le déclenche un jour |

> **Où les comptes affichés viennent.** `novel-details.md` § 11.1 : *« B18's six choices as
> radio rows, each with a running chapter count beside it »*. Le compte de chaque ligne est
> `resolveBulkChoice(choice).length`, appelé sur la liste complète des chapitres du roman
> **au moment où la feuille s'ouvre**. Il n'est ni une estimation, ni un `min`, ni une valeur
> mise en cache : un nombre que le lecteur voit et un nombre que la file applique qui
> divergent, c'est B18 cassé en silence.

### 3.2 Enqueue (couvre **B18**) — six branches, toutes écrites

```
enqueue(novelId, BulkChoice choice):
  chapters = SELECT c.* FROM chapters c
             WHERE c.novel_id = :novelId
             ORDER BY c.ordinal ASC              # ⚠️ jamais ORDER BY number
                                                     # (2-3 § 3.3 : number = -1
                                                     #  illisible et repart par volume)

  # ── branche 1 : le roman n'a aucune ligne chapters ────────────────────────
  if chapters.isEmpty:
    log('queue: no chapter rows for $novelId')    # PAS d'exception : un roman
    return []                                     #   sans liste n'est pas un bug,
                                                  #   c'est un roman qu'on n'a pas
                                                  #   encore ouvert (B12)

  picked = resolveBulkChoice(choice, chapters: chapters.map(toDownloadable))

  # ── branche 2 : le choix ne donne rien (roman tout stocké, 0 non ouvert) ──
  if picked.isEmpty:
    return []                                     # la feuille dit pourquoi ;
                                                  # aucun dialogue d'erreur

  # ── branche 3 : premier emplacement de position ────────────────────────────
  # La file est globale, pas par roman : `queue_items` n'a pas de colonne
  # novel_id, et `architecture.md` § 4.5 n'en prévoit pas. Donc la position est
  # le maximum global + 1, et non « le maximum du roman + 1 ».
  first = (SELECT COALESCE(MAX(queue_position), 0) FROM queue_items) + 1

  # ── branche 4 : insertion, un id par chapitre, dans l'ordre de `picked` ───
  for (i, chapterId) in picked.indexed:
    if alreadyQueued(chapterId):                  # un état != done existe déjà
      continue                                    # → on ne duplique pas (§ 3.2)
    INSERT queue_items (
      id            : newQueueItemId(),           # jamais le chapterId : deux
                                                    #   files du même chapitre
                                                    #   doivent pouvoir coexister
      chapter_id    : chapterId,
      state         : 'queued',                   # default SQL, écrit explicitement
      queue_position: first + i,                  # ⚠️ insertion order, B18
      added_at      : now(),
      attempts      : 0,
      error_code    : ''                          # '' et non NULL : § 4.5
    )
    # ⚠️ PAS DE downloaded_at ICI, PAS DE state='downloading' ICI.
    # La file n'enfile pas, elle ne télécharge pas.

  # ── branche 5 : la sélection est un doublon strict ─────────────────────────
  # HandPicked avec le même chapitre deux fois → une seule ligne.
  # (La barre de sélection est un toggle, donc cela ne peut pas venir de
  # l'interface ; c'est une garantie du résolveur, testée.)

  # ── branche 6 : la source est indisponible ───────────────────────────────
  # Impossible ici : cette fonction ne fait AUCUN appel réseau. La vérification
  # de la connexion est faite par l'appelant (§ 3.3, à l'étape du fetch), jamais
  # à l'enfilement — sinon «.Downloading needs a connection» (novel-details
  # § 11.1) devrait être une vérité que la file vérifie en écrivant.
  return insertedRows
```

**Pourquoi `alreadyQueued` ignore les lignes `done` :** un chapitre `done` est un chapitre
téléchargé, donc `downloadedAt != null`, donc `resolveBulkChoice` l'a déjà exclu. Si une
ligne `done` existait pour un chapitre non stocké — impossible par ADR-022, qui rend
« marque sans fichier » inatteignable — la garde le signalerait au lieu de dupliquer.

### 3.3 La boucle du runner (couvre **B18** : un par un, dans l'ordre)

```
start():
  if _loop != null: return                     # idempotent
  _loop = _drain()

_drain():
  while (true):
    item = await repo.pending().first          # ORDER BY queue_position ASC,
                                               #   état IN ('queued')
                                               #   → UN SEUL chapitre à la fois.
                                               #   ⚠️ jamais `.take(n)`, jamais
                                               #   une Future.wait sur N items :
                                               #   c'est la seule façon dont le
                                               #   « un par un » de B18 tient.
    if item == null: break                    # file vide → la boucle se termine
                                               #   et _loop redevient null

    await repo.markDownloading(item.id)       # queued → downloading, attempts += 1

    # ── le cœur : exactement trois issues possibles ──────────────────────────
    outcome = await source.fetchChapterContent(chapterOf(item))

    switch (outcome):
      BrowseSucceeded(:final html):
        markdown = await converter.cleanAndConvert(html, source: item.sourceId)

        # ⚠️ E18 appartient à 5-3. ICI, on ne fait que le refuser :
        # un chapitre vide n'est PAS stocké et PAS marqué, il est marqué
        # failed avec un code. Le seuil des 100 caractères est une décision de
        # 5-3, pas d'ici — mais le refus, lui, est déjà correct ici.
        if (!markdownHasRealText(markdown)):
          await repo.markFailed(item.id, 'no_real_text')
          continue                             # → chapitre suivant, PAS d'arrêt

        await chapterStore.store(              # 2-3 : fichier PUIS downloadedAt
          chapter: chapterOf(item),
          markdown: markdown,
        )                                      # ⚠️ si cela lève, l'exception
                                               #   remonte : aucune marque n'a
                                               #   été écrite, le chapitre
                                               #   reste non stocké (B6)
        await repo.markDone(item.id)

      BrowseEmpty():
        await repo.markFailed(item.id, 'source_empty')
        continue                               # E8 : pas « zéro résultat »

      BrowseFailed(:final reason):
        await repo.markFailed(item.id, reason.codeName)
        continue                               # 5-3 décidera, selon la cause,
                                               #   s'il faut arrêter la file
                                               #   entière (E7) ou continuer
  _loop = null
```

**Chaque branche, une ligne :**

| Situation | État de l'item | `downloadedAt` | Suite |
|---|---|---|---|
| Fetch réussi, Markdown réel | `done` | **écrit par `2-3`, après le rename** | chapitre suivant |
| Fetch réussi, **zéro texte réel** (E18) | `failed` + `no_real_text` | inchangé | chapitre suivant |
| `BrowseEmpty` (E8) | `failed` + `source_empty` | inchangé | chapitre suivant |
| `BrowseFailed` retriable ou non | `failed` + code de la taxonomie | inchangé | chapitre suivant |
| `ChapterStore.store` lève (stockage, disque) | reste `downloading`, `attempts` incrémenté | inchangé | l'exception remonte à `5-3` |
| La file est vide | — | — | `_loop = null`, `isRunning == false` |

**Le `continue` est le point qui appartient à `5-1` et que `5-3` remplacera.** Un chapitre
illisible ne doit pas arrêter un roman de 400 chapitres ; une perte de connexion, elle, doit
arrêter la file. **La distinction est par cause, pas parSeverity**, et c'est `5-3` qui la
possède. Ne pas écrire ici un `if (reason is NoConnection) break` : ce serait du travail de
`5-3` fait dans le mauvais fichier, et le test de `5-3` ne le couvrirait pas.

### 3.4 Ce que la file n'écrit **jamais** (couvre **B19**, première moitié)

```
# La seule écriture de `chapters.downloadedAt` dans tout le code base :
#   2-3 → FileChapterStore.store()  →  update(chapters).write(downloadedAt: now)
#
# La file écrit `queue_items.state`, `started_at`, `finished_at`, `attempts`,
# `error_code`. Rien d'autre.
#
# Conséquence mécanique de B19 (« Paused, cancelled and unfinished chapters are
# never marked as downloaded ») : un item `queued`, `downloading` ou `failed`
# a TOUJOURS `downloadedAt == null`. Il n'existe aucun chemin de code qui puisse
# produire le contraire, parce qu'il n'existe aucun chemin de code qui écrive
# cette colonne depuis la file.
#
# Et le chemin inverse — `downloadedAt != null` avec un item `queued` — est
# inatteignable : `resolveBulkChoice` exclut les chapitres stockés, donc un item
# `queued` est toujours un chapitre non stocké.
```

**Vérifiable mécaniquement.** `grep -rn 'downloadedAt\|downloaded_at' lib/` doit renvoyer
exactement deux sites d'écriture : `2-3` et le test. Un troisième site est un défaut, et
`5-2`'s plan le fait regarder.

### 3.5 **E14** et **E15** — tracés, hors périmètre de `5-1`

| Edge case | Pourquoi il n'est pas traité ici | Où il est traité |
|---|---|---|
| **E14** — la taille de police du téléphone change pendant une lecture | Le chapitre en cours d'écriture est un fichier texte ; changer la taille de police pendant qu'on l'écrit ne change rien à son contenu. La seule interaction réelle est **la position de lecture**, et elle appartient à `2-6`/`2-8` | `2-8` (le rendu), `2-6` (l'offset) |
| **E15** — l'app se ferme au milieu d'une file de cinquante chapitres | `5-1` écrit la définition de la file dans la base ; ce qui se passe à la réouverture — reset d'un `downloading` en `queued`, statut `paused`, **jamais** auto-reprise — est exactement le sujet de `5-2` | `5-2` (§ 3.1 de ce plan-là) |

**Le seul apport de `5-1` à E15** est le fait qu'il rende la situation *possible et
correcte* : une ligne restée `downloading` est un état **reprenable**, pas un état
corrompu, parce que rien n'a été marqué et que `attempts` compte les tentatives. Si `5-1`
écrivait `state = done` avant `store()`, E15 deviendrait une perte de données.

## 5. Gestion d'état (state management)

| Donnée | Portée | Stockage | Initialisation | Mise à jour |
|---|---|---|---|---|
| Définition de la file | base | `queue_items` | `enqueue()` | `markDownloading/Done/Failed` |
| Position dans la file | base | `queue_items.queue_position` | `MAX + 1` à l'enfilement | **jamais** |
| État d'un chapitre | base | `queue_items.state` (**par nom**) | `'queued'` | par la boucle |
| Tentatives | base | `queue_items.attempts` | `0` | `+1` à chaque `queued → downloading` |
| Compteur `12 of 50` | base, **dérivé** | `count(state='done')` / `count(chapters du roman)` | — | recalculé par le `Stream` |
| Chapitre en cours | **session** | `SerialDownloadQueueRunner.activeItem` | `null` | la boucle |
| Choix en cours dans la feuille | **widget** | `StatefulWidget` local | `NextChapter` | appui sur une ligne |

**Ce qui n'est délibérément pas de l'état** : le total de chapitres et le nombre de
téléchargés. Ils sont `count(...)` sur les lignes, jamais deux colonnes. B14/B48 ont déjà
interdit ce genre de total stocké pour les non-lus ; la logique est identique et la
raison aussi — un total stocké est une seconde source de vérité libre de diverger des
lignes qu'elle compte.

**`isRunning` est de l'état de session, jamais de la base.** C'est la décision qui rend
E15 et E7 possibles : à l'ouverture d'une session, `isRunning == false` par défaut, donc
**aucune reprise automatique n'est possible même par oubli**. Voir `5-2`.

|---|---|---|---|
| **B18** | *« Downloading a novel enqueues its chapters one at a time in reading order. The bulk choices offered are: the next chapter, the next 5 / 10 / 25 chapters, **all unread chapters**, or an explicit set the user selected by hand. ## 7. Pièges à éviter

- **⚠️ Ne pas ajouter de colonne de concurrence à `queue_items`.** Le comportement correct
  (**B18**) est : la boucle prend **un** chapitre à la fois, `pending().first`, en boucle.
  `queue_items` n'a pas de colonne de concurrence et `architecture.md` § 4.5 le dit
  exprès — *« A constant expressed as a column is something an implementation could change,
  so `app_database_test.dart` asserts the column's **absence** »*. Si l'implémentateur pense
  avoir besoin d'une telle colonne, **c'est une question à écrire ici**, pas un changement de
  schéma à faire.
- **⚠️ Ne pas trier par `chapters.number`.** Le comportement correct (**B9**, **B18**) est :
  `ORDER BY ordinal` à l'enfilement, `ORDER BY queue_position` à la lecture. `number` vaut
  `-1` quand il est illisible et repart à chaque volume ; trier par là réordonne les volumes
  et produit une file qui ne se lit pas dans l'ordre.
- **⚠️ Ne pas écrire `downloadedAt` depuis la file.** Le comportement correct (**B6**,
  ADR-022) est : `2-3` l'écrit, après le rename atomique, et rien d'autre. Un
  `state = 'done'` écrit **avant** `store()` produirait un chapitre « téléchargé » sans
  fichier — l'état exact que la colonne existe pour rendre inatteignable.
- **⚠️ Ne pas écrire `state = 'done'` avant `store()`.** Le comportement correct (**B6**) est :
  `markDownloading` → `store()` → `markDone`. Dans l'autre ordre, une exception de stockage
  laisse une ligne `done` pour un chapitre absent, et le compteur `12 of 50` devient un
  mensonge — C8.
- **⚠️ Ne pas dupliquer une ligne de file pour un chapitre déjà en file.** Le comportement
  correct (**B18**) est : `alreadyQueued(chapterId)` puis `continue`. Le lecteur qui appuie
  deux fois sur *Télécharger* ne doit pas voir le chapitre deux fois.
- **⚠️ Ne pas utiliser `chapterId` comme `queue_items.id`.** Le comportement correct est : un
  `id` généré par enfilement. Le même chapitre peut être re-téléchargé (`3-3` propose un
  *re-télécharger* explicite) ; avec `chapterId` comme clé primaire, le second essai
  écraserait le premier.
- **⚠️ Ne pas faire d'appel réseau au moment de l'enfilement.** Le comportement correct
  (**B5**, **C7**) est : `enqueue()` est une écriture locale ; la connexion est vérifiée à la
  première tentative de *fetch*, par `5-3`. Vérifier à l'enfilement obligerait `5-1` à
  détecter le réseau, c'est-à-dire à charger une dépendance dont il n'a pas besoin.
- **⚠️ Ne pas ajouter un état `paused` à `DownloadState`.** Le comportement correct (**B19**)
  est : un article en pause est `queued` **avec la file arrêtée**. Le commentaire de l'enum
  dans `app_database.dart` l'écrit déjà. Ajouter un cinquième état ferait diverger
  `DownloadStateConverter` du commentaire et de `architecture.md` § 4.5
  (`queued | downloading | done | failed`).
- **⚠️ Ne pas faire de `NextChapter` un choix « non ouvert ».** Le comportement correct
  (**B18**) est : `NextChapter` et `NextChapters(n)` filtrent sur « non stocké », et
  `AllUnopened` est **le seul** choix qui parle de lecture. Si `NextChapter` exigeait
  `isRead == false`, il serait indisponible sur un roman entièrement lu — ce que
  `novel-details.md` § 11.1 refuse explicitement.
- **⚠️ Ne pas écrire un `min(5, total)` dans le widget.** Le comportement correct (**B18**,
  **C8**) est : le compte affiché est `resolveBulkChoice(choice).length`. Un compte affiché
  et un compte enfilé qui divergent sont le genre de défaut qui ne se voit qu'au
  quarantième chapitre.
- **⚠️ Ne pas ajouter de « tout sélectionner » à la barre de sélection.** Le comportement
  correct (**B18**) est : « every chapter including ones already read » n'est atteignable que
  par une sélection délibérée, et `novel-details.md` § 11.3 refuse un *select all* parce
  qu'il en est l'exact contraire.
- **⚠️ Ne pas ajouter un état `selected` à `ChapterListTile`.** Le comportement correct est :
  emprunter la grammaire `selected` **déjà déclarée** par `NovelRow` (2dp
  `--color-border-strong` + `--color-accent` 10 %), comme l'écrit `novel-details.md` § 11.3.
  Une variante locale donne deux grammaires de sélection dans l'app.
- **⚠️ Ne pas faire de la boucle un `Future.wait` sur N chapitres.** Le comportement correct
  (**B18**) est : `while` + `pending().first`. Un `Future.wait` est du parallélisme, et du
  parallélisme est une promesse que le design system refuse explicitement — `downloads.md`
  § 2.1 refuse une barre agrégée « because the queue is serial and a single bar would imply
  a parallelism the app does not have ».
- **⚠️ Ne pas mettre `state` dans un `enum` stocké par ordinal.** Le comportement correct est :
  `DownloadStateConverter` **par nom**, et c'est déjà fait. Un ordinal persisté
  remapperait silencieusement l'historique des états après un réordonnancement de l'enum.
