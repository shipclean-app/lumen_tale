## 1. Résumé de la slice

`2-2` prend le **HTML brut** d'un chapitre, produit un chapitre, et le rend au
lecteur. C'est la transformation centrale du produit, et c'est la première fois
que `lib/` touche un contenu tiers.

Trois décisions de fond, et chacune a été payée :

1. **Le convertisseur est écrit ici, sur `package:html`.** Pas de `html2md` — il
   déclare `sdk: >=2.12.0 <3.0.0` sur **toutes** ses versions publiées, donc
   Dart 2 seul. Pas de `h2m` ni `html_to_markdown_ffi` non plus : ce sont des
   liaisons FFI, et ajouter une chaîne d'outils Rust/FFI pour cette étape est un
   mauvais échange dans un lecteur mobile (ADR-003). Il n'existe donc **aucun
   convertisseur de base à « envelopper »** : la marche sur l'arbre `Element`
   **est** le convertisseur.
2. **Les paragraphes ne sont pas que des `<p>`.** Un chapitre FanMTL contient
   **zéro** `<p>` : la prose est faite de nœuds de texte nus séparés par
   `<br><br>`. Un convertisseur qui ne connaît que `<p>` rend un chapitre entier
   en un seul paragraphe — **et il a l'air correct dans un test de fumée**. Cette
   règle a donc sa propre fixture.
3. **`0-4` alimente cette slice, et c'est une arête déclarée.** L'entrée de
   conversion est une liste de **sélecteurs de « décoration »** relevés sur de
   vraies pages : `0-4` enregistre quelles parties d'une page de chapitre sont du
   contenu et lesquelles sont du mobilier. `architecture.md` § 6.6 raconte
   pourquoi cette arête a été ajoutée tard : une slice de recherche dont le but
   déclaré est « informe X » et dont la liste de dépendances est vide est une
   feuille qui n'informe personne.

**User stories couvertes** : US-04 (Lire un chapitre), et US-05 par la qualité du
texte stocké
**Règles métier couvertes** : B8, B10, B44
**Edge cases couverts** : E1, E10, E22

## 2. Contrats de données (code)

### 2.1 Schémas de validation

**Aucun nouveau schéma.** Aucune table, aucune colonne, aucune migration.
`schemaVersion` reste à 1.

Ce que cette slice **lit** :

- `chapters.name` — le titre du chapitre, **stocké verbatim** par `2-1`
  (B10). Le titre du lecteur vient de là, pas du HTML.
- `chapters.url` — relatif, pour reconstruire une provenance si nécessaire.
- le HTML brut rendu par `2-1` — **jamais persisté**, jamais journalisé (B44).

Ce que cette slice **écrit** : rien. Elle rend un `String`. C'est `2-3` qui
l'écrit sur le disque et qui écrit `downloadedAt` **après** le renommage.

### 2.2 Types et interfaces

Le convertisseur vit dans `core/` — `core` n'importe rien d'autre de `lib/`
(`02-architecture.md`), et c'est pourquoi il est testable sans binding de widget.

```dart
// lib/core/pipeline/html_to_markdown.dart
import 'package:html/dom.dart' as dom;

/// One element to drop, and why.
///
/// `04-html-to-markdown.md` règle 2 : le nettoyage est **par source**. Le
/// convertisseur commun retire ce que toute page contient ; une source déclare
/// en plus ce qui lui est propre. `0-4` produit cette liste depuis de vraies
/// pages.
final class RemovalRule {
  const RemovalRule({
    required this.selector,
    required this.why,
    this.matchesSubtree = true,
  });

  /// A CSS selector, per `package:html`. Never a tag name guessed from memory:
  /// `0-4` reads it off a real captured page and records it in
  /// `18-external-contracts.md`.
  final String selector;

  /// Why this element is furniture. **Never empty** — a rule nobody can
  /// justify is a rule nobody should be able to change. This string is
  /// developer-facing and never reaches a user-visible surface (B28).
  final String why;

  /// When true the whole subtree goes; when false only the element's own
  /// tags go and its text stays. `<script>` and `<style>` are the former —
  /// their text is code, not prose.
  final bool matchesSubtree;
}

/// What the source hands over, per call.
final class ConversionRequest {
  const ConversionRequest({
    required this.rawHtml,
    required this.baseUrl,
    this.additionalRemovals = const <RemovalRule>[],
  });

  /// The article HTML returned by `2-1`. **Already extracted** — règle 1 of
  /// `04-html-to-markdown.md`: *Extract first, convert after: always extract
  /// the article element via the source's selector before converting. Never
  /// convert the whole page.*
  final String rawHtml;

  /// The source's `baseUrl`, used to resolve `href` and `src`. Rule 3 of
  /// `04-html-to-markdown.md`: images kept are rewritten to absolute URLs;
  /// links are resolved so the reader is not handed relative ones.
  final Uri baseUrl;

  /// Per-source additions, from `0-4`. Unioned with the shared defaults, never
  /// replacing them.
  final List<RemovalRule> additionalRemovals;
}

/// The result, with the three counts `04-html-to-markdown.md` needs and the
/// caller needs.
final class ConvertedChapter {
  const ConvertedChapter({
    required this.markdown,
    required this.paragraphCount,
    required this.lineBreakCount,
    required this.textLength,
    required this.imagesKept,
  });

  /// Markdown, ready to store. Never empty — an empty markdown is refused
  /// upstream (§ 3.5).
  final String markdown;

  /// **A chapter is "no real text" when nothing readable survives cleaning —
  /// no paragraph, no line break, and fewer than 100 characters of text in
  /// total** (E18, quoted verbatim). These three counts are how that verdict is
  /// computed without storing the text twice.
  final int paragraphCount;
  final int lineBreakCount;
  final int textLength;

  /// Number of `<img>` kept. Zero for every v1 source — règle 3: *By default,
  /// drop decorative images*, and a web novel is prose, almost never images.
  final int imagesKept;

  /// E18 / E22. **Below the threshold means a failure, never a stored chapter.**
  bool get isBelowThreshold =>
      paragraphCount == 0 && lineBreakCount == 0 && textLength < 100;
}

/// The converter. Ours, on `package:html`, for the reasons in § 1.
abstract interface class HtmlToMarkdown {
  /// Deterministic: the same input HTML always produces byte-identical output,
  /// so re-fetching a chapter yields a stable diff (règles 7 de
  /// `04-html-to-markdown.md`, règle « Deterministic » du contrat).
  ConvertedChapter convert(ConversionRequest request);
}
```

**Les deux listes de règles de nettoyage, et où elles vivent.**

```dart
// lib/core/pipeline/removal_rules.dart
import 'package:lumen_tale/core/pipeline/html_to_markdown.dart';

/// Règle « Drop by default » de `04-html-to-markdown.md`. **Structural and
/// universal**: script, style and iframe have no meaning in a chapter body
/// regardless of which site it came from, and B44 makes several of them a
/// safety question rather than a formatting one.
const List<RemovalRule> kDefaultRemovals = <RemovalRule>[
  RemovalRule(selector: 'script', why: 'B44 — code, never prose, never executed'),
  RemovalRule(selector: 'style', why: 'presentation, not content'),
  RemovalRule(selector: 'noscript', why: 'B44 — fallback markup for a runtime we never run'),
  RemovalRule(selector: 'iframe', why: 'B44 — an embedded document, not text'),
  RemovalRule(selector: 'object', why: 'B44 — an embedded document, not text'),
  RemovalRule(selector: 'embed', why: 'B44 — an embedded document, not text'),
  RemovalRule(selector: 'svg', why: 'vector furniture, not prose'),
  RemovalRule(selector: 'nav', why: 'site navigation, never story'),
  RemovalRule(selector: 'aside', why: 'a sidebar, never the chapter body'),
  RemovalRule(selector: 'footer', why: 'site footer, never story'),
  RemovalRule(selector: 'form', why: 'a comment or search form, never story'),
  RemovalRule(selector: 'button', why: 'a control, never story'),
];

/// Per-source removals, from `0-4`. **Empty until `0-4` lands**, and that is the
/// correct state: `0-4` reads real pages and records what is furniture, and an
/// entry invented before that reading is a guess about a site nobody has
/// inspected.
const List<RemovalRule> kFanMtlRemovals = <RemovalRule>[
  // 18-external-contracts.md point 3, measured: an ad <script> sits INSIDE the
  // content div. `kDefaultRemovals` drops it as a <script> — this entry exists
  // so the wrapper div is dropped too, and so the reason is written down.
  RemovalRule(
    selector: 'div[align="center"]',
    why: 'FanMTL wraps its ad script in this; dropping the div keeps the blank line',
  ),
  // ⚠️ COMMENTAIRE À COMPLÉTER PAR 0-4, PAS PAR CE PLAN.
  // `0-4` relève sur les fixtures capturées les sélecteurs de « mobilier » que
  // `.chapter-content` contient malgré tout — le sélecteur de police
  // `.control-action`, les blocs de recommandation, la pagination en fin de
  // chapitre. Chaque entrée porte son `why`, et chaque valeur de `selector`
  // est reportée dans `18-external-contracts.md` avant d'être utilisée.
];
```

### 2.3 Contrats API

**Aucun appel réseau.** Le HTML arrive déjà extrait et déjà assemblé par `2-1`
(un chapitre multi-pages y est joint dans l'ordre du site). Cette slice ne
sait pas ce qu'est une requête.

```dart
// Signature d'entrée, § 2.3 de 2-1 :
Future<BrowseOutcome<String>> fetchChapterContent(Chapter chapter);

// Signature de sortie, consommée par 2-3 :
ConvertedChapter convert(ConversionRequest request);
```

**Une question ouverte ici, et elle est réelle** : `BrowseOutcome` appartient à
`domain`, et le convertisseur à `core`. Or `core` n'importe pas `domain`
(`02-architecture.md`). Le pipeline ne rend donc **pas** de `BrowseOutcome` — il
rend `ConvertedChapter`, et c'est l'appelant (`2-3`, ou l'interactor entre les
deux) qui décide si un chapitre sous le seuil est un échec ou un chapitre. Cette
slice calcule le verdict (`isBelowThreshold`) et **ne l'applique pas**. La
frontière est ainsi nette : la conversion produit un fait, la couche au-dessus
décide d'un politique.

## 3. Algorithmes critiques

### 3.1 Le parcours de bout en bout

```
convertChapter(rawHtml, baseUrl, removals):

  # ── 1. analyser ────────────────────────────────────────────────────────
  # Règle 5 : décoder avec le charset de la réponse ou les balises meta,
  # retomber sur UTF-8. Jamais ASCII supposé. `package:html` décode les entités
  # pendant l'analyse — règle 6, et ne JAMAIS décoder deux fois.
  doc = html_parser.parse(rawHtml)

  # ── 2. le RÉSEAU de règles, pas la liste ────────────────────────────────
  # Règle 2 : « Centralize common patterns in the shared cleaner, but allow
  # source overrides ». L'union, jamais le remplacement : une source ne peut
  # pas réintroduire un <script>.
  for rule in [...kDefaultRemovals, ...removals, ...kFanMtlRemovals]:
      for node in doc.querySelectorAll(rule.selector):
          rule.matchesSubtree ? node.remove() : node.replaceWith(fragmentOnly(node))

  # ⚠️ Règle 2 encore : une suppression par SÉLECTEUR CSS, jamais par contenu
  # de texte. « Le paragraphe qui commence par » est une règle qui casse au
  # premier chapitre publié.

  # ── 3. la marche ───────────────────────────────────────────────────────
  # ⚠️ ITÉRATIVE, avec une pile explicite. Récursion sur `Element.children` est
  # plus courte à écrire et échoue sur un DOM profondément imbriqué — StackError
  # sur un chapitre réel, et E1 demande qu'une liste de 10 000 entrées reste
  # lisible. (voir § 7)
  emitBlock(body)

  # ── 4. normaliser ──────────────────────────────────────────────────────
  # Règle « Whitespace » : fusionner les suites d'espaces dans les nœuds de
  # texte ; rogner les bords de bloc ; JAMAIS plus d'une ligne vide d'affilée.

  # ── 5. compter ─────────────────────────────────────────────────────────
  return ConvertedChapter(
    markdown: out.toString(),
    paragraphCount: out.paragraphCount,
    lineBreakCount: out.lineBreakCount,
    textLength:   out.plainTextLength,   # longueur du texte, balises exclues
    imagesKept:   out.imagesKept,
  )
```

### 3.2 Les paragraphes : `br br` vaut paragraphe (règle « Required behaviour »)

C'est **la** règle de cette slice, et elle a son propre motif de fixture.

```
état de la marche : pendingBreak ∈ {0, 1, 2}

# ── <p> ────────────────────────────────────────────────────────────────
<p>texte</p>            -> \n\n + texte + \n\n      paragraphCount += 1

# ── <br> ───────────────────────────────────────────────────────────────
<br>  suivi de texte    -> «  \n »                lineBreakCount += 1   (coupure
                                                          dure Markdown)
<br>  suivi de <br>     -> pendingBreak = 2, RIEN n'est émis

# ── texte nu ───────────────────────────────────────────────────────────
texte nu, pendingBreak == 2  -> \n\n + texte + \n\n    paragraphCount += 1
                              (c'est le paragraphe que le site veut)
texte nu, pendingBreak == 0  -> tel quel, dans le bloc courant
texte nu, pendingBreak == 1  -> la coupure simple a déjà été émise ; rien de plus

# ── un <br><br> de FIN de document ─────────────────────────────────────
# ⚠️ Il ne crée pas un paragraphe vide. pendingBreak reste en attente et
#   disparaît avec la pile. Un chapitre se terminant par <br><br> ne doit pas
#   se solder par deux lignes vides.
```

**Pourquoi c'est écrit comme ça et pas « `<p>` ou `br br` »** : FanMTL émet
**zéro** `<p>`. Une règle qui teste « est-ce que ce nœud est un `<p>` » ne voit
jamais de `<p>` sur un chapitre réel, et le chapitre entier sort en un seul
paragraphe — qui **semble** correct à la lecture et échoue au test de structure.
D'où la fixture dédiée de § 11.1.

### 3.3 L'école des éléments, toutes branches (règle « Inline » et « Block »)

| Élément | Sortie | Cas particular |
|---|---|---|
| `p` | bloc, `paragraphCount++` | § 3.2 |
| `br` | coupure dure, **ou** séparateur de paragraphe | § 3.2 — le point central |
| `h1`–`h6` | `#` × niveau + espace, bloc | niveau **borné à 6** ; un `h7` en sortie est invalide |
| `em`, `i` | `*texte*` | imbrication gérée par un compteur de profondeur |
| `strong`, `b` | `**texte**` | imbrication gérée de même |
| `code` (inline) | `` `texte` `` | **jamais échappé** |
| `pre` | triple accent grave, contenu brut | **jamais échappé**, règle « Escaping » |
| `a` | `[texte](href résolu)` | href résolu contre `baseUrl` ; **`javascript:` n'est jamais rendu** |
| `img` | **abandonné par défaut** | règle 3 : *By default, drop decorative images*. `imagesKept == 0` |
| `del`, `s` | `~~texte~~` | |
| `blockquote` | `> ` par ligne, bloc | |
| `ul`, `ol` | liste, **imbriquée, indentation correcte** | un niveau = deux espaces, `1.` pour `ol` |
| `hr` | `---`, bloc | |
| `table` | tableau en barres verticales | **repli** sur le texte des cellules si la table est trop irrégulière |

**Branches de `table`, qui sont trois et non une :**

```
table :
  1. chaque ligne a le même nombre de cellules, ≥ 1 colonne, et aucune cellule
     ne contient un saut de bloc  ->  tableau Markdown
       | A | B |
       |---|---|
       | 1 | 2 |
  2. sinon  ->  REPLI : chaque cellule devient un paragraphe, séparée par « — »
       Règle 8 « No data loss » : on perd la forme du tableau, **jamais son texte**.
  3. plus de 200 lignes  ->  REPLI, sans exception.
       Règle « fall back to paragraph text if the table is too irregular to
       represent » : au-delà d'un seuil, « trop irrégulière » est la seule
       description honnête, et le rendu Markdown d'un tableau de 200 lignes
       n'est pas lisible sur un téléphone de 360 dp.
```

**Branches d'un `img`, qui sont trois :**

```
img :
  1. source = kDefaultRemovals + source, donc le défaut est « jeter »  -> rien
  2. si une source conserve ses images :
       src est RÉÉCRIT en absolu contre baseUrl      (règle 3)
       et le fichier est téléchargé par le pipeline de téléchargement,
          PAS par ce convertisseur                 (règle 3, mot pour mot)
  3. une image dont `src` ne peut pas être résolue  ->  jetée, comptée
       dans `imagesKept` ? non. Une image cassée ne doit pas produire un
       `![](…)` que le lecteur verra cassé aussi.
```

### 3.4 Échappement, espaces, déterminisme (règles « Escaping », « Whitespace », 7)

```
ÉCHAPPEMENT
  Échapper les caractères réservés Markdown DANS LES NŒUDS DE TEXTE SEULEMENT,
  et seulement là où un échappement changerait le sens.
  ⇔ JAMAIS à l'intérieur de `pre` / `code`      (règle « Escaping »)

  Réservés : \ ` * _ { } [ ] ( ) # + - . ! | > ~

  « seulement là où » a une contrepartie obligatoire :
  ⚠️ Un chapitre qui parle Markdown ne doit pas être Altégé au point de rendre
  « il a dit \* \* \* » illisible. Donc :

    on n'échappe PAS un caractère qui est entouré d'espaces des deux côtés,
    ni un `*` isolé entre deux espaces, ni un `-` en milieu de phrase.
    On n'échappe que la liste ci-dessus, et seulement quand le caractère est
    adjacent à un autre caractère non-espace.

  Le test `un mot qui contient des astérisques reste lisible` verrouille
  ce compromis.

ESPACES
  dans un nœud de texte : toute suite de [\s\n]+ devient un seul espace
  bords de bloc : rogner
  JAMAIS deux lignes vides d'affilée en sortie
  ⚠️ `&nbsp;` : FanMTL ne l'utilise PAS ; les séparateurs sont des `<br><br>`
     en clair (18-external-contracts.md point 4). Donc aucun travail d'entité
     supplémentaire n'est nécessaire, et aucune n'est inventée.

DÉTERMINISME
  même HTML en entrée -> Markdown identique octet pour octet
  ⇔ AUCUN `DateTime`, aucun aléa, aucun `Set` dont l'ordre d'itération est
    incertain dans la sortie, aucun hachage de map Hast. Une liste, toujours.
  Test : convertir deux fois le même HTML, comparer les deux `String`.
```

### 3.5 Le seuil « pas de vrai texte » (couvre **E22**, E18)

```
isBelowThreshold = paragraphCount == 0
                && lineBreakCount == 0
                && textLength      <  100
```

Les trois conditions sont **conjonction**, pas alternative, et c'est ce qui rend
le seuil sûr :

```
« Extra », une note d'auteur, une fin de volume :
  paragraphCount ≥ 1, donc PAS sous le seuil, même à 40 caractères.
  → E22 : « Stored and read like any other chapter ».

une page dont le sélecteur a été renommé :
  paragraphCount == 0, textLength < 100
  → sous le seuil, donc ÉCHEC, donc rien n'est stocké (B6, E18).

une page qui n'a qu'un saut de ligne et 400 caractères :
  lineBreakCount ≥ 1, donc PAS sous le seuil. Le texte existe, il est mal
  découpé. C'est un rendu imparfait, pas une page vide.

une page entièrement supprimée par les règles de nettoyage :
  paragraphCount == 0, lineBreakCount == 0, textLength == 0
  → sous le seuil → échec.
```

**Ce que cette slice fait, et ne fait pas.**

```
2-2  : calcule isBelowThreshold et RENDE le fait.                § 3.5
2-3  : refuse d'écrire le fichier, ne pose PAS downloadedAt,     § 3.5
       et remonte ParseFailed(chemin) au lieu d'un SourceLayoutChanged
       — parce que le HTML était déjà extractible par la source (2-1 aurait
       rendu SourceLayoutChanged si le conteneur avait manqué), et que la
       cause est ici le texte, pas la structure.

⚠️ Ne PAS appliquer la politique dans cette slice. `2-2` produit un fait ;
   la couche qui possède une base et un disque décide.
```

**Le seuil est-il un entier choisi ou une mesure ?** Il est écrit **dans le
PRD**, pas choisi ici. E18 : *fewer than 100 characters of text in total*. Ce
plan ne le modifie pas et ne le paramètre pas — un seuil paramétré est un seuil
qu'un jour quelqu'un réglera à 0.

### 3.6 La jointure multi-pages, et ce que cette slice voit (couvre **B8**, **E3**)

```
04-html-to-markdown.md règle 4 : « when a chapter is split across multiple
pages, the source must fetch all pages and concatenate content in order
before conversion. »

CE QUI EST FAIT : la JOINTURE.  → `2-1` (§ 3.8 de ce plan)

CE QUI EST FAIT ICI : la CONSOMMATION d'une chaîne déjà jointe.
  L'application ne voit qu'un seul fragment ; elle ne sait pas qu'il y en
  avait trois. C'est correct : la séparation des responsabilités est dans les
  règles, pas dans l'état.

  ⚠️ Ne PAS implémenter de découverte de pagination ici. Le contrat de `2-1`
  est déjà « les fragments, dans l'ordre du site ». Le convertir ne ferait
  qu'ajouter un second endroit où l'ordre peut se tromper.

B8 est donc rendu visible de deux façons, et les deux sont testables :
  1. un HTML contenant deux articles séparés par <br><br> donne DEUX
     paragraphes, pas un — un test le prouve avec une fixture unique
  2. l'ordre du site est préservé : le fragment de la page 3 ne peut pas
     précéder celui de la page 1, parce que `2-1` a déjà ordonné
```

## 5. Gestion d'état (state management)

| Donnée | Portée | Stockage | Initialisation | Mise à jour |
|---|---|---|---|---|
| HTML brut d'un chapitre | slice | `String` en mémoire, **jamais persisté** | le paramètre `rawHtml` | — |
| Markdown converti | slice | `String` en mémoire | `convert()` | — |
| Compteurs du seuil | slice | trois `int` dans `ConvertedChapter` | `convert()` | — |
| `chapters.name` | base | colonne `chapters.name` | posé par `2-1` | **jamais par cette slice** |
| Fichier `.md` | disque | `<support>/chapters/…` | **par `2-3`** | **par `2-3`** |

**Ce qui n'est délibérément pas de l'état** : le HTML brut sur disque. Il est la
plus grande valeur que cette slice manipule, et il est celui qu'il est le plus
temptant de cacher entre deux exécutions pour éviter de re-fetcher. Ce serait
**B5** : rien n'est demandé au site sans que le lecteur l'ait demandé, et
`2-1` refait la requête parce que le lecteur l'a demandée. Le HTML brut
n'entre jamais en base.

**Ce qui n'est pas de l'état non plus** : aucun cache de conversion. Une même
chaîne convertie deux fois rend le même résultat (§ 3.4), donc la seule chose
qu'un cache apporterait serait de la place en base — et `2-3` stocke déjà le
résultat, qui est ce qui compte.

### 6.1 Règles métier (B*)

| ID | Règle (PRD) | Implémentée où | Approche |
|---|---|---|---|
| **B8** | A chapter spread over several pages on a site is presented to the reader as one continuous chapter, with the pages joined in their original order (E3). | § 3.6 | La jointure est faite par `2-1` (`04-html-to-markdown.md` règle 4 impose que ce soit **la source**) et cette slice consomme une chaîne unique. Ce qui reste ici et qui est testable : le joint ne crée pas d'artefact de séparation, et l'ordre du site est préservé. **Ne pas redécouvrir la pagination ici** — un second endroit où l'ordre peut se tromper est un endroit de plus où il se trompera |

### 6.2 Edge cases (E*)

| ID | Cas (PRD) | Approche de gestion | Où |
|---|---|---|---|
| **E1** | Chapter list of extreme length — la liste complète reste dans l'ordre, rien n'est abandonné | Aucun impact sur la **liste** : cette slice ne voit qu'un chapitre. L'impact porte sur le **volume** : un chapitre long donne un `StringBuffer` long, et une marche **itérative** avec une pile explicite plutôt qu'une récursion (une hiérarchie profonde donne un `StackError`, pas un rendu lent) | § 3.1, § 7 |
| **E10** | The same chapter listed twice by a site — les deux sont affichés ; l'application ne fusionne pas et ne supprime pas | Cette slice **ne déduplique rien**, et n'a aucun moyen de le faire : elle ne voit qu'un article déjà extrait, sans liste ni identifiant. Un mot répété dans la prose reste donc deux fois dans le Markdown, ce qui est exactement correct — B10 porte sur la **liste de chapitres**, que `2-1` porte | § 3.1 |
| **E22** | A chapter is legitimately very short — un *Extra*, un *Omake*, une note de fin de volume : **stocké et lu comme un autre**. Le seuil E18 ne doit pas le jeter | Le seuil de § 3.5 est une **conjonction de trois** conditions : `paragraphCount == 0 && lineBreakCount == 0 && textLength < 100`. Un *Extra* a au moins un paragraphe, donc n'est **jamais** sous le seuil, quelle que soit sa longueur. Le test prend une vraie fixture courte de `0-1` et affirme qu'elle franchit le seuil | § 3.5 |

**E18 est également traité ici, et il doit l'être.** `state.json` ne l'attribue pas
à `2-2` — il l'attribue à `0-2` — alors que `roadmap.md` § 8 Wave 2 le nomme
explicitement pour `2-2` : *« Clean and convert a chapter page to stored text,
with the "no real text" threshold rules (B5, B44, E18, E22) »*. **Les deux
documents sont approuvés et ils ne sont pas d'accord**, et la version de Forge
(`roadmap.md`) est la plus précise : le seuil est de la conversion. Cette slice
implémente donc **E18** — le seuil, sa formule et ses trois branches — et le signale
comme divergence à trancher, sans modifier `state.json`.

| ID | Cas (PRD) | Approche de gestion | Où |
|---|---|---|---|
| **E18** | A chapter page contains no real text — absent, vide, ou ne contenant que des espaces réservés : **« no paragraph, no line break, and fewer than 100 characters of text in total »**. Sous le seuil, le chapitre n'est pas stocké comme complet et il est rapporté comme un échec avec réessai | § 3.5 calcule le verdict par la formule ci-dessus et le rend dans `ConvertedChapter.isBelowThreshold`. **Cette slice n'applique pas la politique** — elle ne possède ni disque ni base. `2-3` refuse l'écriture et ne pose pas `downloadedAt` | § 3.5, § 2.3 |

| **C1** | Legal — aucun contenu n'est republié, aucune redistribution | Le convertisseur écrit sur le disque du téléphone et nulle part ailleurs. Aucun appel sortant. Le HTML brut d'un site tiers existe en mémoire pendant la conversion, puis disparaît |

## 7. Pièges à éviter

- **⚠️ Ne pas écrire un convertisseur qui ne connaît que `<p>`.** Le comportement
  correct (`04-html-to-markdown.md` § Required behaviour, et
  `18-external-contracts.md` point 1) est : `<p>` → paragraphe, **et `br br` →
  paragraphe**. Un chapitre FanMTL contient **zéro** `<p>` ; sans la seconde
  règle, le chapitre entier sort en un seul paragraphe qui **paraît** correct.
  C'est pour cela que cette règle a sa propre fixture.
- **⚠️ Ne pas convertir la page entière.** Le comportement correct
  (`04-html-to-markdown.md` règle 1) est : la source extrait d'abord l'élément
  article, et le convertisseur ne voit que ce fragment. Convertir le document
  complet fait entrer dans le texte tout le mobilier du site — et la font
  picker de FanMTL avec.
- **⚠️ Ne pas convertir en Markdown dans `2-1`.** Le comportement correct
  (`03-source-system.md` règle 11) est que `fetchChapterContent` rend du **HTML
  brut**. La conversion est le travail du pipeline partagé, sinon chaque source
  doit réinventer son propre rendu Markdown — ce qu'ADR-003 a précisément décidé
  d'éviter en écrivant le convertisseur ici.
- **⚠️ Ne pas supprimer par contenu de texte.** Le comportement correct
  (`04-html-to-markdown.md` règle 2) est : des **sélecteurs CSS** dans un
  `RemovalRule` avec une raison écrite. « Supprimer le div qui contient 'Suivant' »
  casse au premier chapitre publié qui écrit autrement.
- **⚠️ Ne pas laisser une source remplacer la liste par défaut.** Le comportement
  correct (`04-html-to-markdown.md` règle 2) est l'**union** des règles communes
  et des règles de la source. Une surcharge qui remplacerait la liste
  réintroduirait un `<script>` dans le texte — ce qui est **B44**, pas une
  question de présentation.
- **⚠️ Ne pas surveiller `src` d'une image.** Le comportement correct (**B44**,
  règle 3 de `04-html-to-markdown.md`) est : par défaut les images sont **jetées**,
  et si une source les conserve, le **téléchargement** est le fait du pipeline de
  téléchargement, pas du convertisseur. `imagesKept == 0` sur toutes les sources
  v1 ; un test l'affirme.
- **⚠️ Ne pas suivre un lien trouvé dans la page.** Le comportement correct
  (**B44**) est qu'un lien est **résolu** — c'est ainsi que la pagination
  fonctionne — mais **jamais suivi** par cette slice. Et un `href` `javascript:`
  n'est jamais rendu en Markdown.
- **⚠️ Ne pas marcher l'arbre par récursion.** Le comportement correct
  (`04-html-to-markdown.md` § Required behaviour, et **E1**) est une marche
  **itérative** avec une pile explicite. Une hiérarchie suffisamment profonde
  donne un `StackError` sur un chapitre réel — et le symptôme ressemble à une
  page cassée, donc à `SourceLayoutChanged`, donc à B22 sur un bug de code.
- **⚠️ Ne pas échapper à l'intérieur de `pre` / `code`.** Le comportement correct
  (règle « Escaping ») est d'échapper **uniquement dans les nœuds de texte** et
  **jamais** dans un bloc de code. Un bloc de code Altégé n'est pas du code, et
  la règle 8 « No data loss »preserve les blocs de code.
- **⚠️ Ne pas tout échapper.** Le comportement correct (règle « Escaping », et sa
  moitié « only where an escape would otherwise change meaning ») est
  d'échapper les caractères réservés **adjacents à un caractère non-espace**.
  Échapper chaque `*` d'une phrase transforme un chapitre lisible en un mur de
  barres obliques, et **ça n'est pas** ce que la règle demande.
- **⚠️ Ne pas appliquer le seuil dans cette slice.** Le comportement correct
  (**E22**, § 2.3) est que `2-2` **calcule** `isBelowThreshold` et `2-3`
  **décide**. Le convertisseur ne possède ni disque ni base ; s'il « refusait »,
  il n'aurait nulle part où le dire.
- **⚠️ Ne pas paramétrer le seuil de 100 caractères.** Le comportement correct
  (**E22**, **E18**) est la constante écrite dans le PRD. Un seuil configurable est
  un seuil que quelqu'un réglera un jour à `0`, et ce jour-là tous les *Extra* du
  monde deviendront des échecs.
- **⚠️ Ne pas mettre le HTML brut en base ni dans un cache.** Le comportement
  correct (**B5**, **C4**) est qu'il vit en mémoire pendant la conversion, puis
  disparaît. Le mettre en cache pour éviter un re-fetcher serait une requête que
  personne n'a demandée.
- **⚠️ Ne pas sortir d'itération volontairement.** Le comportement correct
  (**E1**) est : le convertisseur rend **tout** le document, sans troncature et
  sans marque de coupure. Le reader.md § 6 exige *« guaranteed never to
  overflow »*, et sa seule réponse est que la colonne se ré-enveloppe — pas que le
  convertisseur coupe.

**Deux questions ouvertes.**

1. **E18 est attribué à deux slices.** `state.json` le donne à `0-2` — dont la
   responsabilité déclarée est « Record whether FanMTL has an explicit
   empty-result signal » — tandis que `roadmap.md` § 8 Wave 2 le donne à `2-2`
   avec le libellé *« the "no real text" threshold rules »*. Les deux documents
   sont approuvés. **Option la moins coûteuse** : cette slice implémente le
   seuil, parce que c'est la seule des deux dont le code peut le contenir ; `0-2`
   reste le slice qui mesure un fait sur des fixtures. **Question ouverte** :
   faut-il retirer E18 de `0-2` dans `state.json` ?
2. **`kFanMtlRemovals` est à moitié renseignée, volontairement.** Une entrée est
   mesurée (`18-external-contracts.md` point 3). Les autres doivent venir de `0-4`,
   qui lit de vraies pages et enregistre le mobilier résiduel de
   `.chapter-content`. **Question ouverte** : rien n'est inventé ici, et le
   convertisseur fonctionne avec la seule règle par défaut si `0-4` n'a rien
   trouvé de plus. Mais le lecteur verrait alors tout ce que `0-4` n'a pas
   signalé — donc le test « le convertisseur retire le mobilier que `0-4` a
   signalé » doit être écrit **quand `0-4` a répondu**, pas avant.
