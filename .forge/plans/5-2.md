## 1. Résumé de la slice

`5-2` donne au lecteur **les trois contrôles** — pause, reprise, annulation — et règle la
question que ces contrôles posaient : **que survit à la mort du processus ?**

La réponse tient en une phrase, et c'est **B21** : *la définition de la file survit, son
exécution non.* Concrètement :

- **Survit** : les lignes `queue_items`, donc l'ordre, les chapitres restants, `attempts`,
  `errorCode`, les chapitres déjà stockés.
- **Ne survit pas** : la boucle. `isRunning == false` à l'ouverture d'une session, par
  défaut, et **aucun chemin de code ne le remet à `true` tout seul**.
- **Résultat** : à la réouverture, la file est **en pause à l'endroit où elle s'est arrêtée**,
  jamais relancée depuis le chapitre 1. Le lecteur appuie sur *Reprendre*. C'est E7
  littéralement : *« The reader resumes it »*.

**Aucun arrière-plan d'exécution n'existe en v1.** Pas de service, pas de
`workmanager`, pas de notification de téléchargement. `15-performance.md` §Background work
le dit : *« The download queue runs **in-process**, owned by `07-downloads-offline.md` »* —
et `workmanager` est réservé à `6-10` / `6-4`, qui est un autre sous-système avec un autre
cycle de vie (ADR-021).

**User stories couvertes** : US-08 (regarder et contrôler un téléchargement), US-07
**Règles métier couvertes** : B19, B21
**Edge cases couverts** : E15, E19 — et **E7**, qui n'est pas assigné à cette slice dans
`state.json` mais qui la gouverne (§ 6.2).

### 2.2 Types et interfaces

```dart
// lib/domain/downloads/queue_run_state.dart
/// L'état de la file tel que l'écran le voit — **dérivé, jamais stocké**.
///
/// Les trois premiers cas sont de l'état de session (le processus) et les trois
/// suivants sont de l'état de base (les lignes). La frontière est ce qui rend
/// B21 vrai : ce qui est en base survit au kill, ce qui est en session ne survit
/// à rien — et c'est exactement ce qu'E7 veut.
enum QueueRunState {
  /// La boucle tourne. **Inatteignable à l'ouverture d'une session** : E7.
  running,

  /// Le lecteur a suspendu. Distingué de [stopped] par la présence d'un contrôle
  /// *Reprendre* qui reprend **sans explication** ; [stopped] doit dire pourquoi.
  paused,

  /// Arrêtée pour une raison qu'il faut dire : pas de connexion, stockage saturé,
  /// source illisible. C'est E7 qui la nomme le plus souvent.
  stopped,

  /// **Le processus est mort au milieu.** Ce n'est pas un état persisté : c'est
  /// l'observation « il existe une ligne `downloading` au moment où j'ouvre ».
  /// À la première lecture, il est **toujours** converti en [paused].
  interrupted,

  /// Rien à faire : aucune ligne non `done`. La section file n'est pas rendue.
  idle,
}

/// Pourquoi la file s'est arrêtée. **Ce n'est pas une colonne** : c'est le
/// `errorCode` de la ligne qui l'a fait, plus l'observation du processus.
///
/// Les trois valeurs correspondent à `downloads.md` § 8
/// (`no_connection, out_of_storage, cancelled`) plus la source illisible, que
/// B22 exige de nommer.
enum QueueStopReason {
  noConnection('no_connection'),
  outOfStorage('out_of_storage'),
  cancelled('cancelled'),
  sourceUnreadable('source_layout_changed'),
  unknown('');

  const QueueStopReason(this.code);
  final String code;
}

/// La vue qu'un écran consomme. Un seul objet, assemblé par `deriveQueueRunState`
/// (§ 3.1), jamais trois requêtes répétées dans trois widgets.
final class QueueRun {
  const QueueRun({
    required this.state,
    required this.stopReason,
    required this.totalCount,
    required this.doneCount,
    required this.failedCount,
    required this.activeItem,
  });

  final QueueRunState state;
  final QueueStopReason stopReason;

  /// Les deux nombres du header. **Exacts, jamais estimés** (C8).
  final int doneCount;
  final int totalCount;
  final int failedCount;
  final QueueEntry? activeItem;
}
```

```dart
// lib/domain/downloads/queue_run_state_deriver.dart
/// La fonction pure qui décide de l'état affiché. **Toute la logique de cette
/// slice est ici**, et nulle part ailleurs.
QueueRun deriveQueueRunState({
  required List<QueueEntry> entries,
  required bool isRunning,
}) {
  final unfinished = entries.where((e) => e.state != DownloadState.done).toList();
  final done = entries.where((e) => e.state == DownloadState.done).length;
  final failed = entries.where((e) => e.state == DownloadState.failed).toList();
  final downloading =
      entries.where((e) => e.state == DownloadState.downloading).toList();

  // ── 1. rien à faire ─────────────────────────────────────────────────────
  if (unfinished.isEmpty) {
    return QueueRun(
      state: QueueRunState.idle,
      stopReason: QueueStopReason.unknown,
      totalCount: entries.length,
      doneCount: done,
      failedCount: 0,
      activeItem: null,
    );
  }

  // ── 2. le processus est mort au milieu d'un item ────────────────────────
  // ⚠️ On observe `downloading` AVANT de regarder `isRunning`. C'est le seul
  // endroit où l'ordre des tests compte : une ligne `downloading` alors que la
  // boucle ne tourne pas est, par définition, une interruption de processus.
  if (downloading.isNotEmpty && !isRunning) {
    return QueueRun(
      state: QueueRunState.interrupted,
      stopReason: QueueStopReason.unknown,
      totalCount: entries.length,
      doneCount: done,
      failedCount: failed.length,
      activeItem: null,
    );
  }

  // ── 3. la boucle tourne ─────────────────────────────────────────────────
  if (isRunning) {
    return QueueRun(
      state: QueueRunState.running,
      stopReason: QueueStopReason.unknown,
      totalCount: entries.length,
      doneCount: done,
      failedCount: failed.length,
      activeItem: downloading.firstOrNull,
    );
  }

  // ── 4. la boucle ne tourne pas, plus rien en vol ────────────────────────
  // Arrêtée par la perte de connexion ou le stockage (E7, E20) : le motif est
  // dans l'errorCode de la dernière ligne en échec.
  if (failed.isNotEmpty) {
    final lastFailure = failed.last;
    return QueueRun(
      state: QueueRunState.stopped,
      stopReason: reasonFromCode(lastFailure.errorCode),
      totalCount: entries.length,
      doneCount: done,
      failedCount: failed.length,
      activeItem: null,
    );
  }

  // ── 5. la boucle ne tourne pas, aucune ligne en échec ───────────────────
  // → suspension volontaire. Un `unknown` ici se lirait comme une panne ; le
  //   lecteur a peut-être simplement suspendu.
  return QueueRun(
    state: QueueRunState.paused,
    stopReason: QueueStopReason.unknown,
    totalCount: entries.length,
    doneCount: done,
    failedCount: 0,
    activeItem: null,
  );
}
```

## 3. Algorithmes critiques

### 3.1 Ouverture de session — la réinitialisation d'interruption (couvre **E15**, **E7**, **B21**)

C'est l'algorithme le plus important de la slice. Il s'exécute **une fois par session**, au
premier `watch` du provider, et **jamais** autrement.

```
onSessionStart(entries):
  # ── 1. Ramener les lignes en vol à `queued` ─────────────────────────────
  n = repo.resetInterruptedToQueued()
  #    downloadedAt n'est pas touché : un item interrompu n'a jamais été
  #    marqué, donc il n'y a rien à effacer. C'est ADR-022 qui rend cela vrai.
  #    attempts est conservé : B20 compte les essais.

  # ── 2. NE PAS démarrer la boucle ────────────────────────────────────────
  # ⚠️ C'est ici que la plupart des implémentations se trompent. Après l'étape 1,
  # il existe N lignes `queued`. Il est tentant d'appeler `runner.start()`.
  # C'est exactement la promesse qu'E7 interdit :
  #   « It does **not** resume on its own when the connection returns:
  #     the download queue runs in-process and has no background executor.
  #     The reader resumes it. »
  # Donc : isRunning reste false. Rien ne tourne. La boucle attend le geste.

  # ── 3. Ce qui est rendu à l'écran ──────────────────────────────────────
  # deriveQueueRunState(entries, isRunning: false)
  #   → interrupted seulement s'il reste un `downloading`… il n'en reste plus,
  #     l'étape 1 les a tous ramenés. → donc `paused` ou `stopped`.
  #   ⚠️ Conséquence : `interrupted` est un état **transitoire et non rendu**,
  #     visible seulement entre le `SELECT` et le `UPDATE` de l'étape 1. La
  #     colonne `queue.status` de `downloads.md` § 8 le dit : « interrupted is
  #     the state after the process died and is **always reset to paused** on
  #     open, never to running ».
  return pausedOrStopped   # avec doneCount exact et l'InProcessNotice au-dessus
```

**Les quatre issues, une par ligne :**

| Situation à l'ouverture | `resetInterruptedToQueued` | `isRunning` | Rendu |
|---|---|---|---|
| File à 12/50, tuée pendant le chapitre 13 | 1 ligne repassée à `queued`, `attempts` inchangé | **`false`** | `paused`, `12 of 50 downloaded` |
| File à 12/50, tuée **entre** deux chapitres (aucune ligne `downloading`) | 0 ligne touchée | **`false`** | `paused`, `12 of 50 downloaded` |
| File arrêtée par perte de connexion, puis app fermée | 0 ou 1 ligne | **`false`** | `stopped`, `no connection`, *It will not continue on its own* |
| File déjà vide | 0 | `false` | `idle` — la section n'est pas rendue |

**Ce qui ne survit pas, écrit une fois :** le jeton d'annulation en cours, la position dans
le fichier `.part`, l'objet HTTP du chapitre interrompu. **Ce qui survit :** les lignes. Le
`.part` résiduel est ignoré par `2-3`'s `fileFor()` et écrasé au prochain `store()` du
même chapitre — c'est E15 dans `2-3` § 6.2, déjà traité là.

### 3.2 Pause (couvre **B19**)

```
pause():
  # B19 : « Stop before the next chapter. The chapter in flight finishes;
  #         no further chapter is fetched after it. »
  _wantPause = true

  # ⚠️ NE PAS interrompre le chapitre en vol.
  # - le fichier est écrit par rename() (2-3) ; l'interrompre au milieu produit
  #   un .part, pas un chapitre corrompu — mais ce serait du travail inutile ;
  # - le design l'écrit : « The chapter in flight finishes;
  #   no further chapter is fetched after it » (downloads.md § 5) ;
  # - « The running row's controls are absent, not disabled » : pendant
  #   l'écriture, il n'y a rien à mettre en pause.
  # La boucle vérifie _wantPause au SEUL endroit qui compte : juste avant de
  # prendre le chapitre suivant.
```

| Situation | Ce qui se passe | `state` de l'item en vol |
|---|---|---|
| Pause demandée, aucun item en vol | la boucle s'arrête au `pending()` suivant | — |
| Pause demandée, item en vol | le chapitre **finit**, `store()`, `markDone`, puis la boucle s'arrête | `done`, `downloadedAt` écrit |
| Pause demandée deux fois | idempotent | inchangé |
| Pause sur une file déjà en pause | aucune écriture du tout | — |

**Le contrôle du lecteur pendant l'écriture est *absent*, pas désactivé** — c'est l'état
*Read-only* de `downloads.md` § 4, et c'est la seule façon de ne pas promettre une action
impossible. Une action désactivée est une promesse à propos d'une version qui n'existe pas.

### 3.3 Reprise (couvre **B21**, **B20**)

```
resume():
  # ── 1. Refuser si rien à faire ──────────────────────────────────────────
  if no non-done entries: return      # le bouton n'est pas rendu dans ce cas

  # ── 2. Le contrôle de connexion est ici, pas dans `enqueue` ──────────────
  if (!platform.hasConnection):        # E7 / E5
    markStopped(noConnection)          # la file devient `stopped`, pas `paused`
    return                             # ⚠️ AUCUN chapitre n'est démarré.
                                       # « Resume is present and attempting it
                                       #  while offline produces the stopped
                                       #  state with No connection, not a
                                       #  silent no-op » (downloads.md § 8)

  # ── 3. Démarrer au bon endroit — B21 ────────────────────────────────────
  _wantPause = false
  runner.start()
  # pending() renvoie ORDER BY queue_position ASC WHERE state='queued'
  # → le PREMIER chapitre restant, jamais le chapitre 1.
  #
  # ⚠️ C'est B21 qui tient ici, et rien d'autre ne peut le tenir :
  #   • `downloadedAt` sur les chapitres déjà faits → ils ne sont pas `queued`
  #   • la ligne laissée `downloading` → ramenée à `queued` par § 3.1, donc
  #     reprise en **début de chapitre**, pas en milieu de fichier (B20)
  #   • `queue_position` inchangée → l'ordre d'origine est respecté
```

**Les quatre issues :**

| Situation | Résultat |
|---|---|
| File à 12/50, app rouverte, *Reprendre* | le chapitre 13 est repris **depuis le début**, `attempts` passe à 2 |
| Reprise **hors ligne** | état `stopped` + *No connection*, **aucun** fetch, aucun chapitre démarre |
| Reprise alors que la file est vide | le bouton n'existe pas ; l'appel est un no-op silencieux |
| Reprise après un chapter `failed` | l'item `failed` reste `failed` ; seuls les `queued` sont repris. Le *Retry* est `5-3` |

### 3.4 Annulation (couvre **B19**, **B20**)

```
cancel():
  # 1. Confirmation — le dialogue vient de l'écran (downloads.md § 5)
  if (!userConfirmed): return

  # 2. La boucle s'arrête IMMÉDIATEMENT, avant toute écriture
  _cancelled = true
  runner.stopNow()          # B19 : « a cancellation takes effect without a
                            # further action, and no further chapter is fetched
                            # after it »

  # 3. Supprimer les lignes non `done` — l'annulation EST une suppression
  removed = repo.clearUnfinished()     # § 2.2

  # 4. Jeter le fichier partiel du chapitre en vol
  #    2-3 a écrit <ordinal>.md.part ; il n'est pas renommé, donc il n'est pas
  #    un chapitre. Le supprimer est une courtesy, pas une obligation : 2-3 le
  #    fait déjà au prochain store() du même chapitre. Le faire ici rend
  #    l'annulation instantanée et évite qu'un .part sobrevive à des semaines.

  # 5. Ce qui reste
  #    • les lignes `done` : elles restent dans la file ET downloadedAt reste
  #      écrit → les chapitres téléchargés sont gardés (downloads.md § 4)
  #    • les fichiers sur disque : intacts
  #    → snackbar « Download cancelled — 12 chapters kept »

  # ⚠️ 6. Si l'écriture en base échoue :
  #    l'écran montre « Could not cancel. The download is still running. » et la
  #    boucle repart. Une file affichée comme annulée alors qu'elle court, c'est
  #    exactement ce que B19 interdit et le cas (a) de downloads.md § 4.
```

**Les quatre issues d'annulation :**

| Situation | Effet sur les lignes | Effet sur les fichiers | Effet sur `downloadedAt` |
|---|---|---|---|
| File à 12/50, chapitre 13 en vol | 13 lignes non `done` supprimées, 12 `done` conservées | `.part` du 13 jeté, 12 `.md` conservés | 12 restent non nuls, aucun écrit |
| File déjà annulée | 0 ligne supprimée | rien | rien |
| **L'écriture échoue** | **rien n'est supprimé** (transaction drift) | rien | rien — et l'écran **redit** que la file tourne |
| Annulation sur une file `idle` | rien ; le dialogue n'est même pas proposé | — | — |

### 3.5 Le dialogue d'annulation et son échec — pourquoi il est dans la prose du plan

`downloads.md` § 4, cas *Submit error (a)* : *« Cancel fails — the most important one on
this screen: the queue **keeps running**, the switch springs back, and a snackbar says
"Could not cancel. The download is still running." »*. C'est la seule soumission de
l'app dont **l'échec doit inverser l'affichage**, parce que l'inverse afficherait une file
annulée qui continue d'écrire des chapitres. Le § 3.4 étape 2 s'exécute donc **avant**
l'étape 3 : si l'écriture échoue, la boucle **redémarre**, et l'état affiché redevient
`running`. Un test le vérifie (§ 11.1).

**Riverpod** (`05-state-management.md`) : `downloadQueueControlProvider` est **`keepAlive`**
avec la raison écrite dans `5-1` § 4.2 — E7. Il porte `isRunning`, qui est **de la session**,
donc `autoDispose` le ferait passer à `false` au pop d'un écran et présenterait une file en
cours comme arrêtée. **La raison de `keepAlive` est donc E7, pas une commodité.**

`InProcessNotice` vit dans `features/downloads/` et **pas** dans `core/ui/` : aucun autre
écran ne la porte, et `design-system.md` § 2.7 range ce genre de composant local dans la
feature (le précédent existe : `ScheduleNotice` dans `updates.md` § 3, item 6).

### 4.3 États par écran

`downloads.md` § 4 déclare neuf états. Cette slice en porte **trois** ; les six autres
appartiennent à `5-1` (Filled, Empty×2, Load error) ou à `5-3` (Submit error complet,
Offline avec motif, Success).

| État | Ce que cette slice rend | Règle |
|---|---|---|
| **Filled — `paused`** | `QueueRunStateRow` en `--color-warning` **+ icône + le mot « Paused »**, et un `primary` **Resume**. `Pause` disparaît, `Resume` apparaît. **Pas** de dialogue : suspendre est réversible et instantané | B19 |
| **Filled — `stopped`** | `--color-error` **+ icône + le motif en mots** — *Stopped — no connection. 12 of 50 chapters are downloaded.* — puis, **sur la ligne suivante**, *It will not continue on its own when the signal comes back.* Puis un `primary` **Resume** | **E7**, E20, B19 |
| **Filled — `interrupted`** | **Jamais rendu.** L'état existe dans le domaine pour que la réinitialisation de § 3.1 soit testable ; l'écran ne le voit jamais, parce que `downloads.md` § 8 dit *« always reset to `paused` on open, never to `running` »* | E15, B21 |
| **Filled — `idle`** | La `QueueSection` **n'est pas rendue** du tout. Ni ligne « paused », ni bouton *Reprendre* désactivé | `downloads.md` § 4 |

**La position de l'`InProcessNotice` est un choix de design, pas un détail :** elle est
**directement sous le titre, dans tous les états**, au-dessus de `QueueSection`. Ce n'est pas
une note de bas de page et ce n'est pas une boîte de dialogue déjà vue. `downloads.md` § 2.1 :
*« it is the first line under the title, it is always there, and it is repeated inside the
stopped state »*. **Ne pas la déplacer dans les réglages.**

### 4.4 Formulaires

**Aucun.** Les trois contrôles sont des boutons et une confirmation. La seule chose qui
ressemble à un formulaire ici est le message de l'échec d'annulation, et c'est un `SnackBar`
du composant partagé de `core/ui/` — jamais un `ScaffoldMessenger` direct dans la feature
(`09-widgets-ui.md` §Overlays).

## 5. Gestion d'état (state management)

| Donnée | Portée | Stockage | Initialisation | Mise à jour |
|---|---|---|---|---|
| Définition de la file | base | `queue_items` | `5-1` | `clearUnfinished` (annulation) |
| `isRunning` | **session** | état du notifier | **`false`**, toujours | `resume()` → `true` ; fin de boucle / `cancel()` → `false` |
| `_wantPause` | **session** | état du notifier | `false` | `pause()` → `true` ; `resume()` → `false` |
| `stopReason` | **dérivé** | `errorCode` de la dernière ligne `failed` | — | `deriveQueueRunState` |
| `12 of 50` | **dérivé** | `count(state='done')` / `count(entries)` | — | le `Stream` de `5-1` |

**Le tableau ci-dessus est la réponse à « que survit ».** Colonnes 1 et 4-5 : en base, donc
elles survivent. Colonnes 2-3 : en session, donc elles ne survivent à rien — et c'est
**exactement** ce qu'E7 demande, parce que le pire défaut possible serait un `isRunning`
persisté qui redémarre la file tout seul à l'ouverture.

**Pourquoi `isRunning` n'est pas un `Stream` de la base :** parce qu'il décrit un processus,
pas des données. Un `Stream` drift ne peut pas dire « le processus est vivant » ; il peut
seulement dire « une ligne dit `downloading` », ce qui est une **supposition** — c'est
`deriveQueueRunState` qui la convertit en `interrupted`, puis en `paused`.

**Ce qui n'est pas de l'état :** le chapitre en vol est déjà une ligne de la base
(`state = downloading`); la position dans le fichier est un `.part` sur le disque. Aucun
des deux ne mérite une variable en mémoire.

## 6. Traçabilité des règles

### 6.1 Règles métier (B*)

| ID | Règle (PRD, texte intégral) | Implémentée où | Approche |
|---|---|---|---|
| **B19** | *« A download queue can be paused and cancelled. Paused, cancelled and unfinished chapters are never marked as downloaded, and a cancellation takes effect without a further action, and no further chapter is fetched after it. »* | § 3.2 pause, § 3.4 annulation | Pause = drapeau consulté **avant de prendre** le chapitre suivant, donc le chapitre en vol finit et **aucun** chapitre suivant n'est cherché. Annulation = `_cancelled` consulté en premier dans la boucle + `clearUnfinished()` + rejet du `.part`. *« Paused, cancelled and unfinished chapters are never marked as downloaded »* est structurel : la file n'écrit jamais `downloadedAt` (`5-1` § 3.4). *« Takes effect without a further action »* : le drapeau est consulté par la boucle, pas par une action du lecteur |
| **B21** | *« A download queue survives the app being closed and reopened: it continues from where it stopped rather than restarting the novel. »* | § 3.1 et § 3.3 | Ce qui survit est en base, donc la file est définie à la réouverture. Ce qui ne survit pas est `isRunning`. La reprise démarre sur `pending()` — le **premier `queue_position` restant** — jamais sur le chapitre 1. Test : fifty chapitres, kill au 13, reprise → le 13 est le premier récupéré, `attempts == 2` |

### 6.2 Edge cases (E*)

| ID | Cas (PRD) | Approche de gestion | Où |
|---|---|---|---|
| **E15** | *« The app is closed or the phone restarts mid-queue — a fifty-chapter download is interrupted by the app being closed or the phone rebooting. The queue continues from the chapter it reached when the app is opened again; it does not restart the novel (B21). »* | **Traité par cette slice.** `resetInterruptedToQueued()` au premier watch ramène les lignes en vol à `queued` **sans toucher `attempts`**, puis **ne démarre rien**. La file rend en `paused` avec `12 of 50 downloaded`, et le lecteur reprend. Le `.part` résiduel est ignoré par `2-3` | § 3.1, `5-1` § 3.5 |
| **E19** | *« A search genuinely matches nothing — the search is well-formed and the site has no match. An explicit "no results" message, visibly distinct from a failure message (B22, US-02). »* | **Hors périmètre.** `E19` concerne la **recherche dans un site**, qui est `6-2` — une slice *conditionnelle* à `6-11`, donc quelque chose qui n'existe peut-être pas en v1. Cette slice n'a aucun champ de recherche et aucun résultat de recherche. **Ce qu'elle en conserve** est la forme du contraste : un état « rien à faire » et un état « ça n'a pas marché » doivent se distinguer par des mots, pas par une nuance de couleur — c'est la même exigence de B22 que `5-3` applique aux échecs de téléchargement | § 3.4 (forme), `6-2` (contenu) |
| **E7** *(non assigné)* | *« Connection lost mid-queue — the connection drops while a whole-novel queue is running. The queue **stops**, says why, and keeps every chapter already completed. It does **not** resume on its own when the connection returns: the download queue runs in-process and has no background executor. The reader resumes it (B19, B21). »* | **Traité, bien qu'E7 ne soit pas dans `edge_case_ids` de cette slice dans `state.json`** — voir § 7.6. L'absence d'exécuteur d'arrière-plan est la **raison pour laquelle `isRunning` est de la session** : il n'y a rien qui puisse remettre un processus mort en route. `resume()` hors ligne donne `stopped` + `no_connection` sans démarrer un chapitre | § 3.1 étape 2, § 3.3 étape 2 |

### 6.3 Contraintes (C*)

| ID | Contrainte (PRD) | Comment elle est respectée |
|---|---|---|
| **C11** | *« Usage context — reading happens one-handed, on a phone, at night or in transit, frequently with poor or no connectivity (C11 also constrains gestures, text size and error legibility). »* | Pause et annulation sont des boutons à 48dp dans la rangée d'actions. **Aucun geste** — pas de swipe, pas d'appui long. Annuler est la seule action destructive et elle passe par un dialogue nommé |
| **C12** | *« Privacy of failure reporting — the app must make its own failure state obvious enough for that reader to describe it to the owner **in words** — a message that can be read aloud and reported back — and actionable, not merely present. »* | L'état `stopped` nomme la cause en toutes lettres — *Stopped — no connection* — et l'action (*Resume*) est un bouton, pas une suggestion. | **C8** | *« Data loss is structurally accepted — there is no backup and no export (B31, C2). ## 7. Pièges à éviter

- **⚠️ Ne pas démarrer la boucle à l'ouverture de l'application.** Le comportement correct
  (**E7**, **B21**) est : `onSessionStart` réinitialise les lignes en vol et **ne lance
  rien**. C'est le défaut le plus probable de cette slice, parce qu'après la réinitialisation
  il existe des lignes `queued` et que l'instinct dit « vas-y ». Lancer la boucle transformerait
  `B21` (reprend où il s'est arrêté) en « il a téléchargé 40 chapitres pendant que le
  téléphone était dans la poche », ce qu'E7 interdit nommément.
- **⚠️ Ne pas ajouter de colonne `paused`, `cancelled` ou `lastStopReason`.** Le comportement
  correct est : pause = drapeau de session, annulation = **suppression de lignes**, motif =
  `errorCode` de la ligne qui a échoué. `DownloadState` n'a pas d'état `paused` et le
  commentaire de l'enum dans `app_database.dart` l'écrit : *« a paused item is `queued` with
  the queue stopped, not a fourth state »*.
- **⚠️ Ne pas rendre l'état `interrupted` à l'écran.** Le comportement correct
  (**E15**, **B21**) est : `interrupted` existe dans le domaine pour que la réinitialisation
  soit testable, mais `downloads.md` § 8 dit *« always reset to `paused` on open, never to
  `running` »*. Montré tel quel, un lecteur qui rouvre l'app verrait *interrompu* et croirait
  qu'une seconde chose s'est passée.
- **⚠️ Ne pas préserver `attempts` comme si c'était un détail.** Le comportement correct
  (**B20**) est : `resetInterruptedToQueued` remet `state = 'queued'` et **conserve
  `attempts`**, parce que c'est ce compteur qui distingue une reprise d'un premier essai et
  qui alimente le `Retry` de l'écran (*« the attempt count is shown, because a threshold being
  applied is a thing the reader deserves to know about »*).
- **⚠️ Ne pas annuler le chapitre en vol à la pause.** Le comportement correct (**B19**,
  `downloads.md` § 5) est : le chapitre en vol **finit**, puis plus rien n'est cherché.
  Interrompre l'écriture produirait un `.part` et un compteur `downloading` pendant que la
  boucle ne tourne plus — c'est-à-dire exactement l'état `interrupted` qu'E15 réserve à une
  mort de processus, et le lecteur ne saurait plus distinguer « suspendu » de « crashé ».
- **⚠️ Ne pas afficher une file annulée dont la suppression a échoué.** Le comportement correct
  (**B19**, `downloads.md` § 4 *Submit error (a)*) est : la boucle **redémarre**, l'écran
  affiche `running`, et le snackbar dit *Could not cancel. The download is still running.*
  L'ordre du § 3.4 (drapeau d'abord, écriture ensuite) est ce qui rend cela possible.
- **⚠️ Ne pas rendre `Resume` disponible hors ligne en dahaleur de parler.** Le comportement
  correct (**E5**, **E7**) est : `resume()` hors ligne donne l'état `stopped` avec
  `no_connection` et **ne démarre aucun chapitre**. Un bouton qui ne fait rien est un no-op
  silencieux, ce que B24 interdit.
- **⚠️ Ne pas utiliser `workmanager` pour « faire tourner » la file.** Le comportement correct
  est : `workmanager` est réservé à `6-10` / `6-4`, la **vérification manuelle** en job de
  premier plan (ADR-021). `15-performance.md` §Background work : *« `workmanager` runs
  library-update checks and nothing else »*. brancher la file dessus réintroduirait
  exactement la promesse E7 forbids.
- **⚠️ Ne pas faire de l'annulation une suppression de `chapters`.** Le comportement correct
  (**C4**, **B32**, ADR-022) est : supprimer des lignes `queue_items`. Les chapitres déjà
  téléchargés restent, leurs fichiers restent, leurs `downloadedAt` restent.
- **⚠️ Ne pas mettre l'`InProcessNotice` dans les réglages.** Le comportement correct (**E7**)
  est : première ligne sous le titre, dans tous les états, et répétée dans l'état `stopped`.
  `flows.md` § 4.4 la nomme *« the single most likely over-promise in the product »*.
- **⚠️ Ne pas faire du `SnackBar` d'échec d'annulation un `ScaffoldMessenger` local.** Le
  comportement correct (`09-widgets-ui.md` §Overlays, `13-error-handling.md` règle 5) est :
  l'enveloppe partagée de `core/ui/`, qui porte `--color-surface-raised` et `--shadow-sheet`.

### 7.6 Une contradiction dans `state.json`, signalée et non corrigée

`state.json` attribue **E7 à `6-6`** (badge de non-lus, avertissement de titre proche,
recherche par titre). Or E7 est *« Connection lost mid-queue »* : son déclencheur, son
comportement attendu et ses deux règles (**B19**, **B21**) appartiennent entièrement à la
file de téléchargement. `6-6` ne possède aucune file.

Cette slice **traite E7 quand même** (§ 6.2), parce que le laisser de côté produirait une
file qui se relance seule — le défaut que la slice est censée empêcher. Mais **la correction
appartient à `state.json`**, pas à ce fichier, et **ce plan ne modifie pas `state.json`**.
Signalé au propriétaire.

Le même motif apparaît ailleurs : **E19** est assigné à cette slice et à `3-2` mais pas à
`6-2`, qui est la seule slice dont le contenu est *« une recherche qui ne trouve rien »*.
