## 1. Résumé de la slice

`2-3` écrit **un chapitre sur le disque, de façon atomique**, puis marque la ligne
`chapters` correspondante. C'est la slice qui rend `2-4` — la preuve de lecture hors
ligne, la promesse centrale du produit — possible : sans elle, il n'y a rien à lire
sans réseau. Elle ne construit **aucune interface** : elle produit une fonction de
stockage et son test. Elle ne gère pas la file d'attente non plus — c'est `5-1`, qui
dépend d'elle et lui fournit les chapitres dans l'ordre.

L'opération centrale est un **renommage** : le contenu est écrit dans un fichier
temporaire, puis `rename()` le déplace d'un coup. SQLite n'est pastransactionnel sur
le système de fichiers, donc l'ordre des deux écritures — le fichier, puis
`downloadedAt` — **est** la règle B6, pas un détail d'implémentation (ADR-022).

**User stories couvertes** : US-05 (Lire un chapitre), US-07 (Télécharger)

**Règles métier couvertes** : B6, B18, B31
**Edge cases couverts** : E14, E15

### 2.2 Types et interfaces

```dart
// lib/features/downloads/domain/chapter_store.dart
import 'dart:io';

import 'package:path/path.dart' as p;
import 'package:path_provider/path_provider.dart';

/// Where a chapter's `.md` lives, relative to the support directory.
/// `architecture.md` § 4.7: the **support** directory, never the cache
/// directory — the OS may evict a cache directory, and B7 requires a stored
/// chapter to stay readable.
abstract interface class ChapterStore {
  /// Writes [markdown] for [chapter] and marks it downloaded.
  ///
  /// Returns the instant the file became complete. Throws [ChapterStoreException]
  /// on any failure; it never returns a partially-stored chapter.
  Future<DateTime> store({
    required ChapterRecord chapter,
    required String markdown,
  });

  /// The chapter's file, or `null` if it is not present. Used by `2-4`.
  File? fileFor(ChapterRecord chapter);

  /// B33 — delete one chapter's copy and clear its mark. Never touches the
  /// novel row, never touches sibling chapters.
  Future<void> deleteOne(ChapterRecord chapter);
}

/// The minimum this slice needs to know about a chapter. Deliberately not
/// `Chapter`: that is a drift row, and a storage function that takes a row
/// cannot be tested without a database.
final class ChapterRecord {
  const ChapterRecord({
    required this.id,
    required this.novelId,
    required this.ordinal,
  });

  final String id;
  final String novelId;

  /// The site's own order (B9). The filename is built from this, never from
  /// `number`: `number` is `-1` when unparseable, and `-1` would collide
  /// across volumes.
  final int ordinal;
}

final class ChapterStoreException implements Exception {
  const ChapterStoreException(this.reason, {this.cause});
  final String reason;
  final Object? cause;

  @override
  String toString() => 'ChapterStoreException: $reason';
}
```

## 3. Algorithmes critiques

### 3.1 Écriture atomique (couvre **B6**, **E15**)

```
store(chapter, markdown):
  root  = supportDirectory()            # jamais cacheDirectory()
  dir   = root/chapters/<chapter.novelId>
  mkdir -p dir                          # recursive: le novelId peut être imbriqué

  final = dir/<ordinal>.md
  temp  = dir/.<ordinal>.md.part        # MÊME dossier, sinon rename() peut
                                        # traverser deux systèmes de fichiers
                                        # et devenir une copie non atomique

  # ── 1. le fichier, d'abord ───────────────────────────────────────────
  write(temp, markdown)                 # utf8, Platform.\_LINE\_TERMINATOR ? "\n"
  flush(temp)                           # fsync — sans ça, un crash peut laisser
                                        # le fichier vide tout en ayant réussi
  if not exists(temp):                  # une écriture "réussie" qui ne produit
      fail(ChapterStoreException)       # pas de fichier est un succès trompeur
  rename(temp, final)                   # atomique sur le même système de fichiers

  # ── 2. la marque, ensuite ────────────────────────────────────────────
  # ⚠️ L'ORDRE EST LA RÈGLE (ADR-022). Un crash entre les deux étapes laisse
  # un fichier SANS marque — la direction sûre : le chapitre se propose au
  # téléchargement au lieu de s'ouvrir comme complet. L'inverse (marque sans
  # fichier) est inatteignable, et c'est cela qui rend B6 exprimable.
  await db.update(chapters)
    ..where((c) => c.id.equals(chapter.id))
    .write(ChaptersCompanion(downloadedAt: Value(DateTime.now())))

  return thatInstant
```

**Trois branches, toutes explicites :**

| Situation | Ce qui se passe | Pourquoi c'est correct |
|---|---|---|
| Écriture + rename OK | fichier puis marque | B6 : complètement présent **et** marqué |
| Crash / kill entre 1 et 2 | fichier sans marque | le chapitre s'offre au téléchargement ; **B6 ne ment pas** |
| `write` ou `rename` échoue | `ChapterStoreException`, **aucune écriture en base** | B6 : jamais « téléchargé » sans fichier |
| `mkdir` échoue (stockage saturé) | `ChapterStoreException` | E20 appartient à `5-3`, mais l'échec remonte ici |
| Fichier déjà présent | `rename` l'écrase, atomiquement | ré-télécharger un chapitre est idempotent |

### 3.2 Suppression d'un seul chapitre (couvre **B33**)

```
deleteOne(chapter):
  final = <support>/chapters/<novelId>/<ordinal>.md
  if exists(final): delete(final)        # un fichier absent n'est pas une erreur
  await db.update(chapters)..where(id).write(downloadedAt: Value(null))
  # ⚠️ NE PAS supprimer la ligne chapters. B9 exige la liste complète quelle
  # que soit sa longueur : supprimer la ligne ferait perdre la liste de
  # chapitres d'un roman de 10 000 chapitres parce qu'un fichier a été effacé.
```

### 3.3 Ordre d'énumération (couvre **B18**)

Cette slice ne construit pas la file — `5-1` le fait. Elle fixe **l'ordre de lecture**
que `5-1` consommera :

```
Chapters are read ORDER BY ordinal ASC, grouped by novelId.
ordinal is the site's own order (B9). NEVER re-sort by `number`:
  number = -1 when unparseable, and `number` restarts per volume,
  so sorting by it reorders volumes. This was already deleted once.
```

## 6. Traçabilité des règles

### 6.1 Règles métier (B*)

| ID | Règle (PRD) | Implémentée où | Approche |
|---|---|---|---|
| **B6** | Un chapitre est stocké atomiquement : soit complètement présent et lisible, soit pas stocké. Un chapitre partiellement stocké n'est jamais montré comme téléchargé et ne s'ouvre jamais comme complet | `FileChapterStore.store` § 3.1 | `rename()` atomique, puis la marque. Un crash entre les deux laisse un fichier sans marque — la direction sûre |
| **B18** | Télécharger un roman met ses chapitres en file un par un dans l'ordre de lecture | § 3.3 | `ORDER BY ordinal ASC`. **Ne pas re-trier par `number`** : `-1` quand il est illisible, et il repart à chaque volume |
| **B31** | Une nouvelle version préserve la bibliothèque, chaque chapitre téléchargé, toutes les positions de lecture et l'historique | Le **stockage**, ici ; la **preuve**, `gate:upgrade-safety` | Le contenu vit dans le répertoire **support**, jamais cache : le système peut vider un cache, et B7 exige qu'un chapitre reste lisible. `schemaVersion` reste à 1 |

### 6.2 Edge cases (E*)

| ID | Cas (PRD) | Approche de gestion | Où |
|---|---|---|---|
| **E14** | Le changement de taille de police du téléphone survient, chapitre ouvert | **Sans effet ici.** Le fichier est du texte ; la taille de police est un rendu. `2-7`/`2-8` la gèrent, et le décalage de position de B16 est déjà stocké en `reading_positions.offset` | — (hors périmètre, tracé pour qu'il ne soit pas perdu) |

## 7. Pièges à éviter

- **⚠️ Ne pas écrire la marque avant le `rename`.** Le comportement correct (**B6**,
  ADR-022) est : le fichier d'abord, la marque ensuite. L'ordre inverse produit un
  état où le chapitre est marqué téléchargé sans fichier — exactement l'état que la
  colonne existe pour rendre inatteignable.
- **⚠️ Ne pas écrire le fichier temporaire dans le répertoire cache.** Le comportement
  correct (**B6**) est : `.part` dans le **même dossier** que le fichier définitif, sinon
  `rename()` traverse deux systèmes de fichiers et devient une copie, donc plus atomique.
- **⚠️ Ne pas omettre le `flush` avant le `rename`.** Le comportement correct (**B6**,
  **E15**) est : `flush` puis `rename`. Sans ça, un chapitre peut être vide sur disque alors
  que l'écriture a « réussi ».
- **⚠️ Ne pas supprimer la ligne `chapters` quand un fichier est supprimé.** Le
  comportement correct (**B33**, **B9**) est : supprimer le fichier, mettre
  `downloadedAt` à `null`, **garder** la ligne. Sinon la liste de chapitres d'un roman
  disparaît parce qu'un fichier a été effacé.
- **⚠️ Ne pas utiliser `cacheDirectory()`.** Le comportement correct (**B7**) est :
  `getApplicationSupportDirectory()`. Le système peut vider un cache à tout moment.
- **⚠️ Ne pas trier par `number`.** Le comportement correct (**B18**, **B9**) est :
  `ORDER BY ordinal`. `number` vaut `-1` quand il est illisible et repart à chaque
  volume ; trier par là réordonne les volumes.
- **⚠️ Ne pas construire le nom de fichier depuis l'id du chapitre.** Le comportement
  correct (**B6**) est : `<novelId>/<ordinal>.md`, l'`ordinal` du site.
