## 1. Résumé de la slice

`5-3` donne à la file trois comportements qu'elle n'avait pas : **une progression qui
bouge**, **une raison d'arrêt qui se dit**, et **un refus de remplir le disque**.

Elle est aussi la seule slice du projet qui **arrête la file**. C'est le pendant direct de
`5-1` § 3.3, où la boucle fait `continue` sur n'importe quel échec : là, un chapitre illisible
ne doit pas arrêter un roman de 400 chapitres ; ici, une perte de connexion, un site cassé ou
un disque plein **doivent** arrêter. **La distinction est par cause, jamais par gravité
ressentie** — c'est le cœur de § 3.2.

Trois décisions non négociables, chacune avec sa raison :

| Décision | Pourquoi |
|---|---|
| **Le seuil E18 — moins de 100 caractères de texte lisible après nettoyage** | Un *Extra*, une note de fin ou un message d'auteur sont du contenu légitime sur ces sites. Sans seuil, chaque *Extra* deviendrait un échec ; avec un seuil trop bas, une page cassée deviendrait un chapitre. E22 existe pour dire que le test est *« du texte lisible a-t-il survécu »*, pas *« y en avait-il beaucoup »* |
| **La progression bat au plus toutes les 500 ms, et le battement ne déplace pas la barre** | `prd.md` § 7.1 : *« moves at least every 500ms while an item is active »*, et c'est le **seul** de ses objectifs de performance **prouvable en CI**. Mais `downloads.md` § 5 interdit qu'une barre bouge quand rien n'est récupéré — les deux sont vrais en même temps si le battement **réémet la valeur courante**, qui ne change pas |
| **L'espace libre n'est pas affiché** | `downloads.md` § 9 : *« Free space is not displayed — the app has no honest way to read it without a platform channel it has not earned »*. Un chiffre d'espace libre périmé est pire que pas de chiffre. L'app dit *« le téléphone n'a plus de place »* et demande de faire de la place |

**User stories couvertes** : US-08 (regarder et contrôler), US-06
**Règles métier couvertes** : B19 (la moitié « arrêter sans nouvelle action »), B20, B24
**Edge cases couverts** : E17, E18, E20

**⚠️ Ce tableau est une extension de la hiérarchie d'exceptions de `13-error-handling.md`.**
Cette hiérarchie en compte cinq et dit *« Add a subclass only when a caller needs to `on X
catch` it specifically »*. Ici, le caller a besoin de `on StorageFullException catch` pour
deux raisons distinctes : arrêter la file, et formuler *« faites de la place puis
reprenez »* au lieu de *« réessayez »*. **Sans la classe, ces deux phrases sont
indistinguables d'une panne réseau** — et C12 exige que le lecteur puisse les décrire par
mots. Voir § 7.6.

### 2.2 Types et interfaces

```dart
// lib/domain/downloads/chapter_progress.dart
/// La progression d'**un** chapitre. Jamais d'un roman : B18 rend la file
/// séquentielle et `downloads.md` § 2.1 refuse explicitement une barre agrégée
/// (*« a single bar would imply a parallelism the app does not have »*).
final class ChapterProgress {
  const ChapterProgress({
    required this.queueItemId,
    required this.chapterId,
    required this.chapterName,
    required this.receivedBytes,
    required this.totalBytes,
  });

  final String queueItemId;
  final String chapterId;
  final String chapterName;
  final int receivedBytes;

  /// **Nullable, et `null` est une information** : le serveur n'envoie pas de
  /// `Content-Length`. `downloads.md` § 8 : *« Absent → the byte figure is omitted
  /// rather than showing `0`, which is a claim »*. Donc pas de barre en
  /// pourcentage dans ce cas, et **jamais** `0 %`.
  final int? totalBytes;

  /// `null` quand `totalBytes` est `null`. **Jamais** `0.0` par défaut : une barre à
  /// zéro qui n'avance pas est une barre qui ment.
  double? get fraction => totalBytes == null || totalBytes! == 0
      ? null
      : (receivedBytes / totalBytes!).clamp(0.0, 1.0);
}
```

## 3. Algorithmes critiques

### 3.1 La cadence de 500 ms (couvre `prd.md` § 7.1, et le mensonge de la barre)

```
# Le récepteur dio appelle onReceiveProgress(received, total) à chaque morceau.
# Ce qui doit sortir de là :

onReceiveProgress(received, total):
  _current = ChapterProgress(
    queueItemId  : _active.queueItemId,
    chapterId    : _active.chapterId,
    chapterName  : _active.chapterName,
    receivedBytes: received,
    totalBytes   : total > 0 ? total : null,   # ⚠️ 0 → null, jamais 0
  )

  # ── branche 1 : la valeur a changé → on émet maintenant ──────────────────
  if (_current != _lastEmitted):
    _sink.add(_current)
    _lastEmittedAt = now()
    return

  # ── branche 2 : la valeur n'a pas changé → le battement décide ───────────
  # Il y a un Timer.periodic(500ms) actif tant qu'un chapitre est en vol.
  # Il réémet _current, qui est IDENTIQUE à la dernière émission.
  #   → le widget rebuildit
  #   → la valeur rendue est la même, donc **la barre ne bouge pas**
  #   → mais une ligne « figée » reçoit une preuve qu'elle est vivante
  # C'est ce qui satisfait les deux exigences simultanément :
  #   « moves at least every 500ms while an item is active »   (l'émission)
  #   « a bar that moves when nothing is being fetched is a lie » (la valeur)

# ── les trois états du timer, tous écrits ────────────────────────────────────
startHeartbeat():   # au passage de queued → downloading
  if (_heartbeat != null) return
  _heartbeat = Timer.periodic(500ms, (_) { if (_current != null) _sink.add(_current) })

stopHeartbeat():    # à la fin d'un chapitre, et à l'arrêt de la file
  _heartbeat?.cancel()
  _heartbeat = null
  _sink.close() si la file s'arrête           # jamais avant
```

**Pourquoi ne pas simplement émettre à chaque octet :** parce que la cadence doit être
**bornée**, pas seulement atteinte. Une connexion rapide émet des centaines d'événements par
seconde, et chacun déclenche un rebuild de la ligne qui tourne. `15-performance.md` §Lists &
lazy loading : *« Row items must be cheap »*. Le seuil bas est donc de **500 ms entre deux
émissions de valeur modifiée**, et `downloads.md` § 5 dit que la barre *« moves at the
cadence the download reports »* — donc une connexion lente émet **plus** vite que la
requête, pas moins.

> **La distinction à écrire en § 7 :** « au moins une émission par 500 ms » et « la barre
> bouge au moins toutes les 500 ms » **ne sont pas la même exigence**. La seconde est
> impossible à satisfaire honnêtement quand aucun octet n'arrive. C'est la première que
> `prd.md` § 7.1 demande, et c'est celle qui est testable.

### 3.2 Ce qui arrête la file, et ce qui ne l'arrête pas (couvre **E7**, **E20**, **B22**)

La fonction qui décide. Elle est **pure**, donc elle se teste sans réseau, sans base et sans
fichier — ce qui est le seul moyen d'avoir les **douze** cas.

```
/// Retourne VRAI si la file doit s'arrêter après cette cause.
bool shouldStopQueue(String errorCode) => switch (errorCode) {
      'no_connection'      => true,   # E7 : on n'essaie pas le chapitre suivant,
                                        #   il échouerait de la même façon, et le
                                        #   lecteur ne verrait que des échecs
      'rate_limited'       => true,   # règle 6 de 17-security.md : attendre
                                        #   Retry-After, ne pas marteler
      'source_layout_changed' => true, # B22 : 48 échecs identiques = UN site
                                        #   cassé. Une ligne, pas quarante-huit.
      'storage_full'       => true,   # E20 : continuer viderait le disque
      'source_empty'       => false,  # E8 : ce chapitre-là, les autres sont bons
      'no_real_text'       => false,  # E18 : idem
      'parse_failed'       => false,
      'cancelled'          => true,   # 5-2 supprime les lignes de toute façon
      _                   => false,  # un code inconnu n'arrête pas une file
    };
```

**Les douze issues de la boucle, une par ligne** — c'est la table que § 11.1 teste :

| `errorCode` | Item | File | `downloadedAt` | Écran dit |
|---|---|---|---|---|
| `no_connection` | `failed` | **`stopped`** | inchangé | *Stopped — no connection. 12 of 50 chapters are downloaded.* + *It will not continue on its own when the signal comes back.* + **Resume** |
| `rate_limited` | `failed` | **`stopped`**, en attente | inchangé | *Stopped — the site asked us to wait. Try again after 14:05.* + **Resume** |
| `source_layout_changed` | `failed` | **`stopped`** | inchangé | **une seule ligne** : *Lumen Tale could not read Royal Road* (B22), pas une ligne par chapitre |
| `storage_full` | `failed` | **`stopped`** | inchangé | *The phone is out of storage. Free up some space, then resume.* + **Resume** |
| `cancelled` | ligne **supprimée** | `idle` | 12 conservés | *Download cancelled — 12 chapters kept* (`5-2`) |
| `source_empty` | `failed` | **`running`** | inchangé | ligne *Could not download*, **Retry** |
| `no_real_text` | `failed` | **`running`** | inchangé | ligne *Could not download*, **Retry**, **avec le nombre de tentatives affiché** |
| `parse_failed` | `failed` | **`running`** | inchangé | ligne *Could not download*, **Retry** |
| code inconnu | `failed` | `running` | inchangé | ligne *Could not download*, **Retry** |
| `ChapterStore.store` lève `StorageFullException` | **reste `downloading`**, `attempts` incrémenté | **`stopped`** | inchangé | identique à `storage_full` ci-dessus, **sans** créer de ligne `failed` — l'item est encore en vol, il n'a pas été déclaré en échec |
| `ChapterStore.store` lève autre chose | **reste `downloading`** | `stopped` | inchangé | *Stopped* avec le motif générique qui **ne devine pas** |
| la file se vide | — | `idle` | n/`n` | snackbar *The Healer Has Returned is downloaded — 50 chapters.* + **Open** |

> **⚠️ La ligne `failed` est un jugement porté sur le chapitre ; l'arrêt est un jugement
> porté sur la file.** Les deux ne se confondent pas. C'est pourquoi
> `ChapterStore.store` qui lève laisse l'item `downloading` : personne n'a encore dit que le
> chapitre était en échec, on a dit que le téléphone n'avait plus de place.

### 3.3 Le seuil E18 — « du texte lisible », et pourquoi 100 (couvre **E18**, **E22**)

```
hasRealText(String markdown) =>
    markdown.isNotEmpty
    && hasAtLeastOneParagraphOrLineBreak(markdown)
    && visibleCharacterCount(markdown) >= 100
```

| Ce qui survit au nettoyage | `hasRealText` | Pourquoi |
|---|---|---|
| Un chapitre de 2 000 caractères | **vrai** | le cas normal |
| Un *Extra*, une note d'auteur, 480 caractères | **vrai** | E22 : *« real content of a few lines »* |
| 99 caractères | **faux** | sous le seuil : `failed` + `no_real_text` |
| Une page dont l'article est absent → chaîne vide | **faux** | E18 |
| Une page de publicité seul → 60 caractères de *« Sponsored »* | **faux** | pas de paragraphe **et** sous le seuil |
| Un chapitre d'une seule ligne de 140 caractères (notes de traduction) | **vrai** | 140 ≥ 100 ; le seuil est sur le **total**, pas sur le nombre de paragraphes |

**Le test est « du texte lisible a-t-il survécu », pas « y en avait-il beaucoup »** — c'est
la phrase de l'edge case lui-même. Une implémentation qui exige *à la fois* un paragraphe et
100 caractères rejectterait un chapitre légitime d'une seule ligne de 140 caractères, et ce
serait E22 violé. La condition « au moins un paragraphe **ou** un saut de ligne » est un `||`,
pas un `&&`.

**Le seuil est une constante nommée, pas un littéral :**

```dart
// core/utils/reader_cleanliness.dart
/// E18 : sous ce seuil de texte lisible, un chapitre n'est pas stocké comme
/// complet. E22 interdit de monter ce seuil pour « attraper » les pages
/// cassées : un *Extra* et une note d'auteur sont du contenu réel.
const int minimumReadableCharacters = 100;
```

### 3.4 Stockage épuisé — ce que l'app sait et ce qu'elle ne prétend pas savoir (couvre **E20**)

```
# ── 1. Où l'échec apparaît ─────────────────────────────────────────────────
# Trois sites, et il faut les trois :
#   a) mkdir -p  <support>/chapters/<novelId>      → ENOSPC / quota
#   b) write    <ordinal>.md.part                  → ENOSPC / quota
#   c) rename   temp → final                      → ENOSPC / quota (rare)
# Aucun des trois ne peut être deviné : le SE dit « no space left on device ».
# 2-3 les encapsule déjà en ChapterStoreException ; 5-3 est le seul endroit qui
# distingue « plein » de « autre chose », parce que c'est le seul endroit qui
# doit dire au lecteur une phrase différente.

# ── 2. Ce que l'app ne fait PAS ─────────────────────────────────────────────
# ⚠️ Aucun « espace libre : 3,2 Mo ». Ce serait :
#   • un platform channel que le projet n'a pas (« a platform channel it has
#     not earned », downloads.md § 9) ;
#   • un chiffre qui devient faux en quelques secondes sur un téléphone où
#     l'utilisateur décharge une photo — donc pire que rien (C12 : un état
#     d'échec doit être actionnable et vrai).
# Ce qui est honnête : « le téléphone n'a plus de place », le nom du chapitre,
# et l'action « faites de la place, puis reprenez ».

# ── 3. Les trois issues ────────────────────────────────────────────────────
try:
  await chapterStore.store(...)
  await repo.markDone(id)
on StorageFullException catch (e):
  # a) PAS de markFailed : l'item est encore en vol (§ 3.2, ligne 10)
  # b) la file s'arrête
  # c) l'écran affiche StorageFullException.bytesNeeded à côté du chapitre
  # d) le .part éventuel est laissé : 2-3 le supprime au prochain store()
  #    ⚠️ et surtout : aucun downloadedAt n'est écrit, donc le chapitre se
  #    propose au téléchargement au lieu de s'ouvrir comme complet (B6)
  stopWithReason(QueueStopReason.outOfStorage, bytesNeeded: e.bytesNeeded)
```

### 3.5 `Retry` — un chapitre, pas une file (couvre **B24**, **B20**)

```
retry(queueItemId):
  # downloads.md § 5 : « Re-fetch that chapter alone, and only that one.
  #   It re-enters the queue and runs in reading order among the others. »
  #
  # ⚠️ Ce n'est PAS « vider la file et relancer ». C'est une ligne remise à
  # `queued` avec une **nouvelle** queue_position — la dernière, donc la file
  # de lecture — et `attempts` **conservé** puis incrémenté au démarrage.
  #
  # Et ce n'est PAS « retélécharger depuis le disque » : 07-downloads-offline.md
  # règle 3 exige un *re-download* explicite qui efface et refait, et ce n'est
  # pas la même chose qu'un Retry d'un chapitre qui n'a jamais abouti.
```

| Situation | Effet |
|---|---|
| `Retry` sur un chapitre `failed` | `state = queued`, `queue_position = MAX + 1`, `attempts` conservé, `error_code = ''` |
| `Retry` sur un chapitre `downloading` | **absent du tout** — l'état *Read-only* : pendant l'écriture il n'y a rien à rejouer |
| `Retry` sur un chapitre `done` | **absent du tout** — il est stocké ; la suppression et le re-téléchargement explicite sont `3-3` et B33 |
| `Retry` qui échoue encore | `failed` de nouveau, **mot identique**, `attempts` incrémenté et **affiché** |
| `Retry` hors ligne | `stopped` / `no_connection`, aucun fetch |

**Pourquoi `attempts` est affiché.** `downloads.md` § 9 (E18) : *« The attempt count is
shown, because a threshold being applied is a thing the reader deserves to know about »*. Un
chapitre qui échoue à la deuxième tentative et un qui échoue à la première ne sont pas le
même défaut, et un lecteur à qui on ne dit pas *combien de fois* ne peut pas décrire le
problème (C12).

### 3.6 Deux romans homonymes (couvre **E17**)

`E17` est *« Two novels with the same title, from different sites »*. Cette slice est la
seule de la file à en être concerné, parce que c'est la seule qui regroupe des chapitres de
plusieurs sources sous une seule notion de file. La réponse est **structurale et vérifiable** :

```
# La file est indexée par chapterId, et chapterId dérive du novelId, qui
# contient le sourceId (architecture.md § 4.1, B2). Donc :
#
#   « Mother of Learning » chez Royal Road  → chapterId  a3f1…:412
#   « Mother of Learning » chez FanMTL      → chapterId  7d40…:412
#
# Aucun code de la file ne lit `chapters.title`. Aucune requête ne fait
# GROUP BY titre. Le seul groupement est par `chapterId`.
#
# Conséquence : deux files distinctes, jamais fusionnées, et un compteur
# « 12 sur 50 » par file — jamais un total agrégé sur deux romans homonymes.
# C'est B2 rendu mécanique.
```

**Test** : deux romans de même titre, deux sources, trois chapitres enfilés dans chacun ; les
six lignes coexistent et `deriveQueueRunState` les compte séparément. Une file par
`novelId`, donc **une seule `QueueSection`** à l'écran à la fois — `downloads.md` § 3 en
montre une seule, et c'est cohérent.

## 5. Gestion d'état (state management)

| Donnée | Portée | Stockage | Initialisation | Mise à jour |
|---|---|---|---|---|
| Octets reçus du chapitre en vol | **session** | champ du notifier | `0` | `onReceiveProgress` |
| Taille totale | **session** | champ du notifier | `null` | `onReceiveProgress` |
| Motif de l'échec | **base** | `queue_items.error_code` | `''` | `markFailed` |
| Nombre de tentatives | **base** | `queue_items.attempts` | `0` | `markDownloading` |
| Progression affichée | **dérivé** | le `Stream` de `ChapterProgress` | — | § 3.1 |
| Espace libre du téléphone | **inexistant** | — | — | — (voir § 3.4) |

**La ligne « espace libre » est là pour être vide.** C'est une décision de conception
enregistrée dans un tableau d'état, parce que le jour où quelqu'un veut l'ajouter, la
question *« où ça se met ? »* aura déjà une réponse : **nulle part**, et voici pourquoi.

**Ce qui n'est pas de l'état :** la taille totale en base. Elle vient de la réponse HTTP du
chapitre courant, elle vaut pour ce chapitre, et la garder au-delà serait la description
d'une réponse qui n'existe plus.

## 6. Traçabilité des règles

### 6.1 Règles métier (B*)

| ID | Règle (PRD, texte intégral) | Implémentée où | Approche |
|---|---|---|---|
| **B19** | *« A download queue can be paused and cancelled. Paused, cancelled and unfinished chapters are never marked as downloaded, and a cancellation takes effect without a further action, and no further chapter is fetched after it. »* | § 3.2 (colonne « arrête la file ») | *« No further chapter is fetched after it »* est rendu par `shouldStopQueue`, une fonction **pure** dont la valeur `true` fait sortir la boucle avant le `pending()` suivant. Les quatre causes qui arrêtent (`no_connection`, `rate_limited`, `source_layout_changed`, `storage_full`) n'ont **aucune** branche qui prenne le chapitre suivant |
| **B20** | *« A download interrupted by loss of connection or by the app closing leaves the affected chapter unstorable-as-complete; the chapter is fetched again from the start rather than completed from a partial state. »* | § 3.2, § 3.5 | Une interruption **ne marque rien** : `downloadedAt` est écrit par `2-3` et nulle part ailleurs, et l'item reste `downloading` ou passe `failed` **sans** marque. Le rejeu est un `queued` neuf, donc `2-3` repart d'un `.part` neuf : **jamais** de reprise en milieu de fichier, jamais d'append |
| **B24** | *« Any action that can fail shows an error the user can read and act on, together with a way to try again. No action fails silently to a blank screen or a silent spinner. »* | § 3.1, § 3.2, § 3.5 | Chaque `errorCode` a **une phrase en mots et une action** : `no_connection` → *Stopped* + **Resume** ; `storage_full` → *faites de la place* + **Resume** ; `no_real_text` / `source_empty` → *Retry* sur cette ligne. Aucune n'est une bare sans étiquette, aucune n'est un échec muet. Et `Retry` qui échoue encore **réaffiche le même motif** avec `attempts` incrémenté |

### 6.2 Edge cases (E*)

| ID | Cas (PRD) | Approche de gestion | Où |
|---|---|---|---|
| **E18** | *« A chapter page contains no real text — the site returns a page whose article element is absent, empty, or holds only placeholders. **A chapter is "no real text" when nothing readable survives cleaning** — no paragraph, no line break, and fewer than 100 characters of text in total. Below that threshold the chapter is not stored as complete; it is reported as a failure with a retry (B6, B22). The threshold exists because a legitimately short chapter is common on these sites — end notes, an "Extra", an author's afterword — and must never be mistaken for a broken one (see E22) »* | `hasRealText` § 3.3, seuil nommé `minimumReadableCharacters = 100`. Un article absent → chaîne vide → `failed` + `no_real_text` + **Retry**, **aucun** fichier écrit, **aucune** marque. La file **continue** : un chapitre cassé n'arrête pas un roman de 400 chapitres | § 3.3, `5-1` § 3.3 |
| **E20** | *« The phone runs out of storage mid-download — a queue exhausts the available space. The queue stops, says why, keeps every already-completed chapter, and never records a partial chapter as complete (B6). »* | `StorageFullException` + `shouldStopQueue('storage_full') == true` § 3.2 et § 3.4. La file **s'arrête**, dit *the phone is out of storage*, propose **faire de la place puis reprendre**, **n'affiche pas d'espace libre** (`downloads.md` § 9), et **n'affiche pas le dialogue de refus** — ce dialogue est pour l'enfilement refusé (`updates.md` § 4), pas pour une file déjà partie. Tous les chapitres terminés restent | § 3.4 |
| **E17** | *« Two novels with the same title, from different sites — the library or a catalogue holds two identically titled novels. They remain two distinct novels, each opening its own site; they are never merged (B2). »* | **Traitée structurellement** § 3.6. La file est indexée par `chapterId`, qui dérive de `novelId`, qui contient `sourceId` (B2). Aucun `GROUP BY` sur un titre, aucune lecture de `chapters.title` dans la file. Deux files distinctes, deux compteurs, **jamais** un total agrégé | § 3.6 |

### 6.3 Contraintes (C*)

| ID | Contrainte (PRD) | Comment elle est respectée |
|---|---|---|
| **C6** | *« No server, no support, no telemetry means the app has no way to learn why it failed. Failures must therefore be recognisable on the device and reported there (B24, B22). »* | C'est la raison d'être de `errorCode` **typé** plutôt que d'un message libre. Un `switch` sur huit causes donne huit phrases françaises et anglaises distinctes (B28), et l'écran peut dire *« Lumen Tale n'a pas pu lire Royal Road »* sans que le lecteur ait à traduire un code |
| **C8** | *« Data loss is structurally accepted — there is no backup and no export (B31, C2). An interrupted or partially written download must therefore never be presented as complete (B6, E6, E7). »* | Un chapitre sous le seuil E18 n'est **jamais** écrit. Un `store()` qui lève laisse l'item sans marque. La barre rend `null` et non `0.0` quand la taille est inconnue, donc elle ne prétend pas une progression qu'elle n'a pas. La section **Failed** compte exactement les chapitres qui n'ont pas abouti |
| **C12** | *« The app must make its own failure state obvious enough for that reader to describe it to the owner **in words** — a message that can be read aloud and reported back — and actionable, not merely present. »* | Chaque cause a **un nom et une action** : *Stopped — no connection*, *The phone is out of storage*, *Could not read Royal Road*. Et le nombre de tentatives est affiché, parce qu'« il a échoué deux fois » et « il a échoué une fois » ne se décrivent pas de la même manière |
| **C11** | *« Reading happens one-handed, on a phone, at night or in transit, frequently with poor or no connectivity »* | La ligne `stopped` porte le motif **en toutes lettres** et non une icône seule — à 360dp, dans le noir, sur un téléphone tenu d'une main. *Retry* est à 48dp. Aucune barre de progression ne demande d'interprétation |
| **C5** | *« The only technical user cannot write code »* | Aucun réglage caché, aucun `settings` de file, aucun bouton « forcer ». Un site cassé se répare par un nouvel APK (`17-security.md` règle 5 : *stop and ask the owner*) |
| **C4** | *« Store only what is needed to read a chapter the user asked for »* | Un `Retry` ne réécrit rien hors du `.part` de son propre chapitre, et `source_empty` / `no_real_text` n'écrivent **rien du tout** |

## 7. Pièges à éviter

- **⚠️ Ne pas distinguer les échecs par « gravité ».** Le comportement correct est :
  `shouldStopQueue(String errorCode)` — une fonction **par cause**, testable sans réseau.
  Un `if (attempts > 3) break` produit une file qui s'arrête sur un chapitre difficile et
  continue sur un site mort, ce qui est l'inverse de B22.
- **⚠️ Ne pas créer une ligne `failed` par chapitre quand le site est cassé.** Le
  comportement correct (**B22**) est : `source_layout_changed` arrête la file **au premier
  chapitre** et l'écran montre **une** ligne *Lumen Tale could not read Royal Road*.
  Quarante-huit lignes identiques sont illisibles et disent la même chose quatre fois.
- **⚠️ Ne pas écrire `markFailed` quand `ChapterStore.store` lève.** Le comportement correct
  (§ 3.2, ligne 10) est : l'item reste `downloading`, et c'est la **file** qui s'arrête avec le
  motif. Un item `failed` dit « ce chapitre est mauvais » ; ce qui est mauvais, c'est le
  téléphone.
- **⚠️ Ne pas afficher l'espace libre.** Le comportement correct (`downloads.md` § 9) est :
  *« Free space is not displayed — the app has no honest way to read it without a platform
  channel it has not earned »*, et un chiffre périmé est pire que pas de chiffre.
- **⚠️ Ne pas monter le seuil E18.** Le comportement correct (**E18** + **E22**) est :
  `minimumReadableCharacters = 100`, sur le **texte lisible total**, avec une condition
  « au moins un paragraphe **ou** un saut de ligne ». Monter le seuil transforme chaque
  *Extra* en échec ; exiger un paragraphe **et** 100 caractères rejectte une note d'auteur
  légitime d'une seule ligne.
- **⚠️ Ne pas mettre `0` là où la taille est inconnue.** Le comportement correct
  (`downloads.md` § 8) est : `totalBytes = null` quand le serveur n'envoie pas de
  `Content-Length`, et `fraction` vaut `null`. `0` est une **affirmation** — il dit
  « zéro octet sur zéro », ce qui est faux.
- **⚠️ Ne pas faire bouger la barre sur un battement.** Le comportement correct
  (`prd.md` § 7.1 + `downloads.md` § 5) est : le battement de 500 ms **réémet la valeur
  courante**, qui est identique, donc la barre ne bouge pas. Faire avancer la barre pour
  qu'elle « bouge » serait un mensonge sur la quantité téléchargée.
- **⚠️ Ne pas émettre un progress à chaque octet sans borne.** Le comportement correct
  (`15-performance.md` §Lists) est : au plus une émission de **valeur modifiée** par
  fenêtre de 500 ms. Sur une connexion rapide, une émission par morceau reconstruit des dizaines de fois par seconde la ligne qui tourne.
- **⚠️ Ne pas mettre `Retry` sur un chapitre `downloading` ou `done`.** Le comportement
  correct (`downloads.md` § 4 *Read-only* et § 5) est : **absent**, pas désactivé. Pendant
  l'écriture il n'y a rien à rejouer ; un chapitre `done` est stocké, et sa suppression
  avec re-téléchargement explicite est B33, pas Retry.
- **⚠️ Ne pas faire de `Retry` un « vider la file et relancer ».** Le comportement correct
  est : une seule ligne remise à `queued`, en **fin** de file, avec `attempts` conservé.
- **⚠️ Ne pas agréger deux romans homonymes.** Le comportement correct (**E17**, **B2**) est :
  la file est groupée par `chapterId`, jamais par titre, et `QueueSection` montre **une**
  file à la fois.
- **⚠️ Ne pas afficher le dialogue de stockage refusé pendant une file déjà partie.** Le
  comportement correct (`updates.md` § 4) est : ce dialogue est pour l'**enfilement** refusé —
  *« The download did not start »*, **rien n'est enfilé** — tandis qu'une file en cours qui
  manque de place affiche l'état `stopped` avec *faites de la place, puis reprenez*.
  Confondre les deux fait croire à l'utilisateur qu'aucun chapitre n'a été téléchargé.
- **⚠️ Ne pas journaliser le texte d'un chapitre.** Le comportement correct
  (`17-security.md` règle 9, `13-error-handling.md` règle 6) est : les logs portent l'id du
  chapitre, l'id de la source et le code d'erreur — **jamais** le texte, **jamais** le titre.
- **⚠️ Ne pas ajouter un `PlatformChannel` pour l'espace libre.** Le comportement correct
  (`09-widgets-ui.md` §Platform behavior : *« No homebrew `MethodChannel` without a strong
  reason »*) est : pas de canal. Si la raison devient forte, c'est une ADR, pas une ligne de
  widget.

### 7.6 Un ajout à la hiérarchie d'exceptions, et sa justification

`13-error-handling.md` dit *« Keep the hierarchy **small**. Add a subclass only when a caller
needs to `on X catch` it specifically »*. Cette slice ajoute **une** classe,
`StorageFullException`, et voici le `catch` qui la justifie :

```dart
} on StorageFullException catch (e) {
  // 1) arrêter la file — impossible à distinguer si la classe n'existe pas,
  //    parce que `ChapterStoreException` couvre aussi les pannes d'E/S ;
  // 2) dire « faites de la place » au lieu de « réessayez » — C12 exige
  //    que les deux soient des phrases différentes ;
  // 3) afficher `bytesNeeded` — `architecture.md` § 5.2 dit que `StorageFull`
  //    *carries* « bytes needed ».
}
```

**Si l'implémentateur juge que `NetworkException` suffit**, il n'a qu'à le démontrer : le
test `retry qui échoue encore` et le test `no_connection vs storage_full` de § 11.1 sont les
deux qui le départagent. **Ce qui n'est pas acceptable** est l'inverse : catcher
`AppException` et regarder `e.message.contains('space')`. C'est un `String` de libre-texte
dans un switch, et `13-error-handling.md` l'interdit explicitement.
