## 1. Résumé de la slice

`0-5` est **la tranche qui rend les dix-huit écrans atteignables**. Ce n'est pas
une tranche d'interface : c'est une tranche de **routage**.

L'état actuel le dit en une ligne. `lib/main.dart` exécute un `MaterialApp` avec
les delegates, `supportedLocales`, `localeListResolutionCallback` et deux
thèmes — **et pas de `home:`**. Donc `2-4`, la preuve de lecture hors ligne,
c'est-à-dire l'affirmation entière du produit, n'avait rien sur quoi se monter.

`architecture.md` § 3.1a chiffre le trou :

> « Eighteen screens, fourteen routes, a five-item nav, and no slice whose job
> was to assemble them. … `grep -in 'shell\|bottom nav\|go_router\|bootstrap'
> architecture.md` returned **one** hit: the § 1.2 folder-tree comment. »

Cinq livrables, et **rien d'autre** :

| Livrable | Détail |
|---|---|
| La table de routes | les routes de `design-system.md` § 3.5, **verbatim**. `/reader/…` et `/onboarding` sont **hors du shell** et ne portent pas de barre d'onglets |
| La barre de navigation | cinq éléments dans l'ordre d'ADR-018, lu depuis l'enregistrement `set-nav` de `state.json` — **pas re-dérivé ici** |
| `MaterialApp.router` | remplace le `MaterialApp` de `main.dart`, **en conservant** `localeListResolutionCallback` et la chaîne de repli FR (B28) |
| Le bootstrap | `main.dart` cesse d'être une démonstration de localisation et devient un point d'entrée |
| **Rien d'autre** | aucun import de `features/`. `app/` n'importe le shell que lui-même |

L'ordre de navigation vient de deux endroits qui concordent — ADR-018 et
`state.json`'s `set-nav` — et `0-5` ne les départage pas :

> « The bottom nav — Five items in ADR-018's order, from `state.json`'s `set-nav`
> record — **not re-derived here, because a second source of truth for nav order
> is the defect ADR-018 was written to end**. »

**User stories couvertes** : US-13 (français et anglais) — le shell est le seul
endroit où les deux langues sont résolues.
**Règles métier couvertes** : **B4**, **B28**, **B30**
**Edge cases couverts** : **E11**, **E12**

### 2.2 `AppRoutes` — les chemins, centralisés

`09-widgets-ui.md` convention 10 : « Route paths are **centralized** (e.g.
`app/router/app_routes.dart`) — never write path literals like `'/novel/$id'` in
features ». `conventions.md` § Conventions de nommage donne l'exemple exact :
`AppRoutes.readerFor(novelId, chapterId)`. Ce fichier est donc celui-là.

```dart
// lib/app/router/app_routes.dart
/// Every path in the app, in one place.
///
/// `09-widgets-ui.md` convention 10: features never write a path literal.
/// The paths themselves are transcribed from `design-system.md` § 3.5,
/// which is the authority — this file does not choose them.
abstract final class AppRoutes {
  // ── the five bottom-nav destinations ────────────────────────────────
  // Order is ADR-018's, read from `state.json`'s `set-nav` record. It is
  // NOT re-derived here: a second source of truth for nav order is the
  // defect ADR-018 exists to end.
  static const String library = '/library';
  static const String updates = '/updates';
  static const String history = '/history';
  static const String browse = '/browse';
  static const String more = '/more';

  // ── inside a destination ─────────────────────────────────────────────
  static const String novelDetails = '/library/novel/:novelId';
  static const String novelChapter = '/library/novel/:novelId/chapter/:chapterId';
  static const String sourceBrowse = '/browse/:sourceId';
  static const String sourceGenre = '/browse/:sourceId/genre/:genre';
  static const String sourceUnavailable = '/browse/:sourceId/unavailable';
  static const String downloads = '/more/downloads';
  static const String settings = '/more/settings';
  static const String settingsReader = '/more/settings/reader';
  static const String settingsAbout = '/more/settings/about';

  // ── OUTSIDE the shell — no tab bar ───────────────────────────────────
  static const String reader = '/reader/:novelId/:chapterId';
  static const String onboarding = '/onboarding';

  // ── builders, never string interpolation at the call site ────────────
  static String novelDetailsFor(String novelId) =>
      '/library/novel/$novelId';

  static String sourceBrowseFor(String sourceId) => '/browse/$sourceId';

  static String sourceGenreFor(String sourceId, String genre) =>
      '/browse/$sourceId/genre/$genre';

  static String sourceUnavailableFor(String sourceId) =>
      '/browse/$sourceId/unavailable';

  static String readerFor(String novelId, String chapterId) =>
      '/reader/$novelId/$chapterId';

  static String settingsReaderPath() => '/more/settings/reader';

  static String settingsAboutPath() => '/more/settings/about';
}
```

plutôt que deviné :

| Chemin | D'où il vient | Où il est consommé |
|---|---|---|
| `/browse/:sourceId/unavailable` | `source-unavailable.md` § 1 le déclare comme sa route, et dit explicitement « The route lives under `/browse/` … Recorded rather than silently resolved » | routage par `3-1`, rendu par la tranche de `source-unavailable` |
| `/more/settings/reader` | `settings.md` § 5 « Push `/more/settings/reader` » ; `settings-reader.md` § 1 `Route` | routage par `settings`, rendu par la tranche `settings-reader` |
| `/more/settings/about` | `settings.md` § 5 ; `settings-about.md` § 1 `Route` | idem |
| `/library/novel/:novelId/chapter/:chapterId` | `design-system.md` § 3.5 **seulement** | **personne.** Voir § 7, question ouverte 1 |

### 2.3 La coquille — `StatefulShellRoute.indexedStack`

`design-system.md` § 3.5 : « one `StatefulShellRoute` per bottom-nav
destination so each tab keeps its own scroll position and back stack ». C'est
`StatefulShellRoute.indexedStack`, dont le `index` **est** l'ordre ADR-018.

```dart
// lib/app/router/app_router.dart
import 'package:flutter/material.dart';
import 'package:go_router/go_router.dart';

import 'app_routes.dart';
import '../shell/app_shell.dart';
import 'placeholder_screen.dart';

/// The app's single router.
///
/// Every screen in the project is a row of this table, and every screen slice
/// adds or fills exactly one. This file is the **only** place a `GoRoute`
/// exists; features push `AppRoutes.readerFor(...)` and nothing else.
abstract final class AppRouter {
  /// One navigator key per bottom-nav branch.
  ///
  /// `StatefulShellRoute.indexedStack` keeps one `Navigator` per branch; the
  /// key is what lets a feature push onto a specific branch's stack from
  /// outside it (e.g. the reader is pushed on the *current* branch so back
  /// returns where the reader came from — `design-system.md` § 3.4: "Reader:
  /// no transition in").
  static final List<GlobalKey<NavigatorState>> branchKeys =
      List<GlobalKey<NavigatorState>>.generate(
    AppNavDestinations.length,
    (int i) => GlobalKey<NavigatorState>(debugLabel: 'branch-$i'),
    growable: false,
  );

  static GoRouter build() {
    return GoRouter(
      initialLocation: AppRoutes.library,
      debugLogDiagnostics: false,
      routes: <RouteBase>[
        // ── the shell: five branches, ADR-018's order ─────────────────
        StatefulShellRoute.indexedStack(
          builder:
              (
                BuildContext context,
                GoRouterState state,
                StatefulNavigationShell shell,
              ) => AppShell(navigationShell: shell),
          branches: <StatefulShellBranch>[
            _branch(0, AppRoutes.library, const PlaceholderScreen(
              screenKey: AppRoutes.library,
            )),
            _branch(1, AppRoutes.updates, const PlaceholderScreen(
              screenKey: AppRoutes.updates,
            )),
            _branch(2, AppRoutes.history, const PlaceholderScreen(
              screenKey: AppRoutes.history,
            )),
            _branch(3, AppRoutes.browse, const PlaceholderScreen(
              screenKey: AppRoutes.browse,
            )),
            _branch(4, AppRoutes.more, const PlaceholderScreen(
              screenKey: AppRoutes.more,
            )),
          ],
        ),

        // ── OUTSIDE the shell: no tab bar, no back stack of a tab ────
        GoRoute(
          path: AppRoutes.reader,
          parentNavigatorKey: branchKeys.first,
          builder: (BuildContext context, GoRouterState state) =>
              const PlaceholderScreen(screenKey: AppRoutes.reader),
        ),
        GoRoute(
          path: AppRoutes.onboarding,
          builder: (BuildContext context, GoRouterState state) =>
              const PlaceholderScreen(screenKey: AppRoutes.onboarding),
        ),
      ],
      // ── no red screen, no blank page (B24) ─────────────────────────
      errorBuilder: (BuildContext context, GoRouterState state) =>
          const PlaceholderScreen(screenKey: 'unknown-route'),
    );
  }

  static StatefulShellBranch _branch(
    int index,
    String path,
    Widget child,
  ) {
    return StatefulShellBranch(
      navigatorKey: branchKeys[index],
      routes: <RouteBase>[GoRoute(path: path, builder: (_, _) => child)],
    );
  }
}
```

raccourcis qu'un plan exécutable ne doit pas garder, et ils sont corrigés en
§ 3.6. Les lire maintenant, les corriger là-bas.

### 2.4 Les cinq destinations — données, pas dessin

`design-system.md` § 3.2 donne pour chacune le libellé EN/FR, la fréquence et la
centralité. `state.json`'s `set-nav` record donne la même chose sous forme
structurée, et c'est **lui** la source que `0-5` lit.

```dart
// lib/app/router/app_nav_destinations.dart
import 'package:flutter/material.dart';

import '../../l10n/generated/app_localizations.dart';
import 'app_routes.dart';

  history(
    path: AppRoutes.history,

    icon: Icons.history_outlined,
    selectedIcon: Icons.history,
  ),
  browse(
    path: AppRoutes.browse,
    rank: 4,
    frequency: 3,
    centrality: 3,
    icon: Icons.explore_outlined,
    selectedIcon: Icons.explore,
  ),
  more(
    path: AppRoutes.more,
    rank: 5,
    frequency: 2,
    centrality: 1,
    icon: Icons.more_horiz_outlined,
    selectedIcon: Icons.more_horiz,
  );

  const AppNavDestination({
    required this.path,
    required this.rank,
    required this.frequency,
    required this.centrality,
    required this.icon,
    required this.selectedIcon,
  });

  final String path;
  final int rank;
  final int frequency;
  final int centrality;
  final IconData icon;
  final IconData selectedIcon;

  /// The localized label. **Never a literal** — `16-i18n.md` rule 1.
  ///
  /// `navMore` does not exist in the ARB files today and this slice adds it;
  /// see § 7, question ouverte 3.
  String label(AppLocalizations l10n) => switch (this) {
        AppNavDestination.library => l10n.navLibrary,
        AppNavDestination.updates => l10n.navUpdates,

        AppNavDestination.browse => l10n.navBrowse,
        AppNavDestination.more => l10n.navMore,
      };

/// The order ADR-018 fixes. `AppNavDestination.values` is declaration order,
/// which is the enum's rank order — and `rank` is asserted against it in § 3.7.
const List<AppNavDestination> appNavDestinations = AppNavDestination.values;
```

### 2.5 `AppScaffold` — le composant que personne ne possède

`design-system.md` § 2.8 définit `AppScaffold` avec six emplacements, et
**seize fichiers d'écran l'utilisent**. Aucune tranche ne le construit :
`architecture.md` § 3.1 ne le liste nulle part. C'est un trou de la même famille
que la table de routes, et `0-5` — qui est *la* tranche de coquille — le prend.

```dart
// lib/app/shell/app_scaffold.dart
import 'package:flutter/material.dart';

/// `design-system.md` § 2.8, verbatim.
///
/// Six slots, three states. **A screen sets `titleBar` OR `readerChrome`,
/// never both** — that is the component's whole rule, and it is why the reader
/// is not a screen with a title bar plus a toolbar.
///
/// `bottomNav` is set by `AppShell` alone, through this class's own
/// `bottomNavigationBar` parameter; a feature never passes one.
class AppScaffold extends StatelessWidget {
  const AppScaffold({
    super.key,
    this.titleBar,
    this.content,
    this.floatingAction,
    this.bottomNav,
    this.persistentStatus,
    this.readerChrome,
    this.showBottomNav = true,
    this.state = AppScaffoldState.default_,
  });

  /// Title bar. `null` in the `immersive` state.
  final PreferredSizeWidget? titleBar;

  final Widget content;
  final Widget? floatingAction;

  /// Present on main destinations only. The shell passes it; nothing else.
  final Widget? bottomNav;

  /// Download progress, above `bottomNav` — `design-system.md` § 2.8's
  /// `persistentStatus` slot. Owned by the downloads slice (`5-3`), supplied
  /// here.
  final Widget? persistentStatus;

  /// The reader's own chrome. **Mutually exclusive with `titleBar`.**
  final PreferredSizeWidget? readerChrome;

  final bool showBottomNav;

  final AppScaffoldState state;

  @override
  Widget build(BuildContext context) {
    return Scaffold(
      appBar: switch (state) {
        AppScaffoldState.immersive => readerChrome,
        _ => titleBar,
      },
      // `09-widgets-ui.md` § Platform behavior: `SafeArea(bottom: false)`
      // when a bottom nav is present, because the nav handles its own inset.
      body: SafeArea(bottom: showBottomNav, child: content),
      floatingActionButton: floatingAction,
      bottomNavigationBar: showBottomNav
          ? Column(
              mainAxisSize: MainAxisSize.min,
              children: <Widget>[
                if (persistentStatus != null) persistentStatus!,
                if (bottomNav != null) bottomNav!,
              ],
            )
          : null,
    );
  }
}

enum AppScaffoldState {
  /// `titleBar` + `content` + `bottomNav`.
  default_,

  /// `readerChrome` instead of `titleBar` AND `bottomNav`.
  immersive,

  /// a download is running: `persistentStatus` appears above `bottomNav`.
  busy,
}
```

### 2.6 `AppShell` — les cinq onglets

```dart
// lib/app/shell/app_shell.dart
import 'package:flutter/material.dart';
import 'package:go_router/go_router.dart';

import '../router/app_nav_destinations.dart';

/// The bottom navigation bar and nothing else.
///
/// Five destinations, ADR-018's order, one `NavigationBar`. No drawer —
/// `design-system.md` § 3.1: "a drawer would hide the destinations that carry
/// the loop".
///
/// **No rail, ever — ADR-019 excluded it from the product.** ≥600dp the bar
/// stays at the bottom and stays five items (`design-system.md` § 3.2). There
/// is **no** width at which a rail becomes correct here: putting one back is
/// not a responsive decision, it is the thing ADR-019 removed.
class AppShell extends StatelessWidget {
  const AppShell({super.key, required this.navigationShell});

  final StatefulNavigationShell navigationShell;

  @override
  Widget build(BuildContext context) {
    return Scaffold(
      body: navigationShell,
      bottomNavigationBar: NavigationBar(
        selectedIndex: navigationShell.currentIndex,
        // `design-system.md` § 3.4: horizontal slide, `--duration-normal`
        // 200ms, `--ease-standard`. `go_router` owns the transition; this
        // slice does not add an `AnimationController` on top of it.
        onDestinationSelected: (int index) => navigationShell.goBranch(
          index,
          // Tapping the tab the reader is already on pops that branch to its
          // root — the platform behaviour, and it is the only way back from a
          // deep stack without a back button.
          initialLocation: index == navigationShell.currentIndex,
        ),
        destinations: <NavigationDestination>[
          for (final AppNavDestination d in appNavDestinations)
            NavigationDestination(
              icon: Icon(d.icon),
              selectedIcon: Icon(d.selectedIcon),
              label: d.label(AppLocalizations.of(context)),
            ),
        ],
      ),
    );
  }
}
```

**⚠️ Deux défauts dans ce listing, corrigés en § 3.6** : l'import
`AppLocalizations` manque, et `Scaffold` sans `AppScaffold` dupliquera le
`SafeArea` de l'écran enfant.

### 2.7 `main.dart` — le bootstrap

**The bootstrap resolves the store, and this plan is solely responsible for it.**

`theme-type` declares

```dart
final appThemePreferencesProvider = Provider<AppThemePreferences>(
  (ref) => throw UnimplementedError('overridden at bootstrap — 0-5'),
);
```

**This plan is the only place `overrideWithValue` exists.** Implementing `0-5`
and `theme-type` as written, with a synchronous `runApp`, produces an app that
**throws on the first frame** — the first frame being the first theme read. This
was invisible because both plans pass every gate: `coverage-check.js` checks
headings and ids, and `check_plans.py` checks that a section contains Dart.

| Decision | Consequence |
|---|---|
| `main` is `async` and awaits | `SharedPreferences` is resolved **once**, before any route exists |
| Every later read is then synchronous | a **screen-level** settings-store load error is **unreachable** — the failure is a *bootstrap* failure, not a screen state (`settings.md` § 4, struck for exactly this reason) |
| `MissingPluginException` is not caught | an app that cannot persist a setting must not pretend it can |

**`localeListResolutionCallback` reste ici.** `16-i18n.md` règle 5 dit
« `_resolveLocale` in `lib/main.dart` », et `architecture.md` § 3.1a dit que
`MaterialApp.router` « **keeping** the existing `localeListResolutionCallback` et
le **FR fallback chain** (B28) ». Il n'est donc **pas** déplacé.

```dart
// lib/main.dart — replacement
import 'package:flutter/material.dart';
import 'package:flutter_localizations/flutter_localizations.dart';
import 'package:flutter_riverpod/flutter_riverpod.dart';
import 'package:shared_preferences/shared_preferences.dart';

import 'app/router/app_router.dart';
import 'app/theme/app_theme_preferences.dart';
import 'l10n/generated/app_localizations.dart';

/// Bootstrap for Lumen Tale.
///
/// Wiring only: localisation, theme, router. Feature code lives under
/// `features/` and is reachable only through `app/router/app_router.dart`.
///
/// ⚠️ **`main` is `async` and it AWAITS — load-bearing, not stylistic.**
/// `theme-type` declares
/// `appThemePreferencesProvider = Provider((ref) => throw
/// UnimplementedError('overridden at bootstrap — 0-5'))`, and **this plan is
/// the only place that override exists.** A synchronous `runApp` leaves the
/// throw live and the app dies on the first read of the theme, which is the
/// first frame.
Future<void> main() async {
  WidgetsFlutterBinding.ensureInitialized();

  // Throws MissingPluginException where the plugin is absent, and that is the
  // correct outcome: an app that cannot persist a setting must not pretend it
  // can. Nothing in this screen's states catches it — it is a bootstrap failure.
  final prefs = await SharedPreferences.getInstance();

  runApp(
    ProviderScope(
      overrides: [
        appThemePreferencesProvider.overrideWithValue(
          AppThemePreferences(prefs),
        ),
      ],
      child: const LumenTaleApp(),
    ),
  );
}

/// Root widget.
class LumenTaleApp extends StatelessWidget {
  const LumenTaleApp({super.key});

  @override
  Widget build(BuildContext context) {
    return MaterialApp.router(
      // `go_router` holds the one instance. Not a provider: navigation state
      // is the router's, and `05-state-management.md` forbids a provider
      // modifying another one's state.
      routerConfig: AppRouter.build(),
      onGenerateTitle: (BuildContext context) =>
          AppLocalizations.of(context).appTitle,
      localizationsDelegates: const <LocalizationsDelegate<Object>>[
        AppLocalizations.delegate,
        GlobalMaterialLocalizations.delegate,
        GlobalWidgetsLocalizations.delegate,
        GlobalCupertinoLocalizations.delegate,
      ],
      supportedLocales: AppLocalizations.supportedLocales,
      localeListResolutionCallback: _resolveLocale,
      theme: _theme(Brightness.light),
      darkTheme: _theme(Brightness.dark),
    );
  }

  ThemeData _theme(Brightness brightness) => ThemeData(
        colorScheme: ColorScheme.fromSeed(
          seedColor: const Color(0xFF4A5D9E),
          brightness: brightness,
        ),
      );
}

/// **B28's fallback chain.** French is this project's primary locale, so an
/// unsupported system locale resolves to French rather than silently falling
/// back to the ARB template (`en`).
///
/// Unchanged from the pre-`0-5` bootstrap, and it stays here on purpose:
/// `16-i18n.md` rule 5 names this function and this file.
Locale _resolveLocale(
  Iterable<Locale>? preferredLocales,
  Iterable<Locale> supportedLocales,
) {
  for (final Locale preferred in preferredLocales ?? const <Locale>[]) {
    for (final Locale supported in supportedLocales) {
      if (preferred.languageCode == supported.languageCode) {
        return supported;
      }
    }
  }
  return const Locale('fr');
}
```

### 2.8 Contrats API

**Aucun appel réseau, aucune base, aucune clé de prefs.** Cette tranche n'a aucun

```dart
// Consommé par 3-1, 3-2, 3-3, 2-4, 3-4, 3-5, 5-1, 5-2, 5-3, 6-1..6-7
```

## 3. Algorithmes critiques

### 3.1 Résoudre un chemin vers un écran — la règle unique

Il y a **une seule** règle de routage dans cette tranche, et toutes les tranches
d'écran la suivent. Elle est courte parce qu'elle est complete.

```
resolve(path):
  path == '/library'                             -> branche 0, LibraryScreen
  path == '/updates'                             -> branche 1, UpdatesScreen
  path == '/history'                             -> branche 2, HistoryScreen
  path == '/browse'                              -> branche 3, BrowseSourcesScreen
  path == '/browse/<sourceId>'                   -> branche 3, BrowseGenreScreen
  path == '/browse/<sourceId>/genre/<genre>'     -> branche 3, BrowseCatalogueScreen
  path == '/browse/<sourceId>/unavailable'       -> branche 3, SourceUnavailableScreen
  path == '/more'                                -> branche 4, MoreScreen
  path == '/more/downloads'                      -> branche 4, DownloadsScreen
  path == '/more/settings'                       -> branche 4, SettingsScreen
  path == '/more/settings/reader'                -> branche 4, SettingsReaderScreen
  path == '/more/settings/about'                 -> branche 4, SettingsAboutScreen
  path == '/library/novel/<novelId>'             -> branche 0, NovelDetailsScreen
  path == '/library/novel/<n>/chapter/<c>'       -> branche 0, § 7 question 1
  path == '/reader/<novelId>/<chapterId>'        -> HORS SHELL, ReaderScreen
  path == '/onboarding'                          -> HORS SHELL, OnboardingScreen
  path == '/sources'                             -> ABSENT de la v1 (§ 3.4)
  path == '/stats'                               -> ABSENT de la v1 (§ 3.4)
  otherwise                                      -> errorBuilder, jamais une page
                                                    blanche (B24)
```

**Chaque branche, y compris les sorties.**

| Situation | Ce qui se passe | Pourquoi c'est correct |
|---|---|---|
| Un chemin du tableau | l'écran correspondant, dans la bonne branche | le cas nominal |
| `/reader/…` | **hors du shell** : pas de barre d'onglets, pas de pile d'onglet | `design-system.md` § 3.5 : « (outside the shell — no tab bar) ». Le lecteur est une destination, pas un onglet |
| `/onboarding` | hors du shell | idem. Et `settings.md` § 5 l'ouvre **sur l'étape 2**, pas sur l'étape 1 — un état d'un écran, pas une route |
| `<sourceId>` inconnu sous `/browse/…` | **rediriger vers `/browse`** | `source-unavailable.md` § 8 : « Unknown → the router cannot resolve the route and falls back to `/browse`; **never** an empty page » |
| `<novelId>` inconnu sous `/library/novel/…` | écran de détails qui rend son état « absent », **jamais** une page blanche | B24. Le rendu est le travail de `3-2` ; le shell ne fait que ne pas l'empêcher |
| Un chemin qui n'existe pas | `errorBuilder` : `commonErrorTitle` / `commonErrorBody` / `commonRetry` — les trois clés **existent déjà** dans les deux ARB | B24 : « No action fails silently to a blank screen or a silent spinner ». Les trois chaînes sont des clés existantes, aucune n'est inventée |
| `/sources`, `/stats` | **pas de route en v1** | `design-system.md` § 3.5 : « removed 2026-10-02 with slices 6-9 and 6-8 ». Les deux reviennent en v2. Voir § 7, question ouverte 4 : `more.md` § 3 liste encore des lignes `Stats` et `Sources` |
| Un lien profond vers `/library/novel/x/chapter/y` | § 3.4 | la seule route de `design-system.md` § 3.5 qu'aucun écran ne réclame |

### 3.2 Résoudre la locale — la chaîne de repli FR

```
_resolveLocale(preferredLocales, supportedLocales):

  for preferred in preferredLocales ?? []:
      for supported in supportedLocales:
          if preferred.languageCode == supported.languageCode:
              return supported
              # ⚠️ COMPARAISON PAR CODE DE LANGUE, JAMAIS PAR CHAÎNE
              # "fr_CA" ne correspond pas a Locale("fr") par egalite de
              # chaine. C'est le languageCode qui rapproche, et c'est ce qui
              # fait que fr_CA tombe sur le francais.

  return Locale('fr')                     # B28 : repli FRANCAIS

  # ⚠️ JAMAIS le fallback implicite de MaterialApp.
  # Sans callback, une locale non reconnue retombe sur la premiere
  # supportedLocales, qui est `en` — le modele ARB. B28 demande le francais.
  # C'est exactement ce que 16-i18n.md regle 5 dit, et c'est la raison pour
  # laquelle la callback existe.
```

**Les branches.**

| Situation | Résultat | Règle |
|---|---|---|
| `preferredLocales == [Locale('fr')]` | `Locale('fr')` | nominal |
| `preferredLocales == [Locale('en')]` | `Locale('en')` | nominal |
| `preferredLocales == [Locale('fr','CA')]` | `Locale('fr')` | E12, par code de langue |
| `preferredLocales == [Locale('de')]` | `Locale('fr')` | **B28**, pas `en` |
| `preferredLocales == [Locale('ja','JP')]` | `Locale('fr')` | idem |
| `preferredLocales == null` ou vide | `Locale('fr')` | idem |
| le téléphone change de langue pendant l'app ouverte | `MaterialApp` reconstruit avec la nouvelle locale, **sans perte d'état** | **E12** : « the app's text, including every error message, follows the new language, with no loss of library, downloads or progress ». La perte viendrait d'un `ProviderScope` remonté ou d'un routeur reconstruit : `main()` n'est appelé qu'une fois, et `AppRouter.build()` est appelé **une fois** dans `build` de la racine |

### 3.3 La barre d'onglets — ce qu'elle fait et ce qu'elle ne fait pas

```
onDestinationSelected(index):
  shell.goBranch(
    index,
    initialLocation: (index == shell.currentIndex),
  )

  # Cas 1 : on tape un AUTRE onglet
  #   -> goBranch(index, initialLocation: false)
  #   -> la pile de CET onglet est conservee ; l'onglet reprend ou il etait.
  #   C'est la raison d'etre de StatefulShellRoute :
  #   design-system.md § 3.5 "so each tab keeps its own scroll position and
  #   back stack".
  #
  # Cas 2 : on tape l'onglet DEJA actif
  #   -> goBranch(index, initialLocation: true)
  #   -> la pile de cet onglet est ramenee a sa racine.
  #   C'est le comportement plateforme, et c'est le seul chemin de retour
  # depuis une pile profonde sans bouton retour.
  #
  # ⚠️ NE PAS AJOUTER third argument `onEntered` avec une logique de scroll.
  # Chaque ecran fait son restore de position ; le shell ne touche pas aux
  # ecrans (architecture.md § 3.1a : "No feature import").
  #
  # ⚠️ NE PAS animer la selection.
  # design-system.md § 3.3 : "Visibility: never" pour le fil d'Ariane, et
  # § 3.4 ne donne qu'un slide horizontal cote navigation. Un
  # AnimatedSwitcher sur l'onglet ajouterait une durree que le design system
  # ne declare pas.
```

### 3.4 Deux routes à ne pas créer, et une à ne pas inventer

Ce sont les trois décisions que cette tranche prend **par prudence**, chacune
écrite pour qu'un implémentateur ne les reprenne pas à l'envers.

**`/more/sources` et `/more/stats` — absentes.**

`design-system.md` § 3.5 le dit dans le tableau lui-même :

> `← v1. /more/sources and /more/stats were removed 2026-10-02 with slices
> 6-9 and 6-8; both screens are designed and return in v2.`

Et `architecture.md` § 3.1 explique pourquoi : **B1** dit quels sites livrent, il
ne dit rien de masquer un site ; aucune règle de la v1 n'a besoin de
`sources.enabled`. Les fichiers d'écran `sources.md` et `stats.md` existent et
sont complets — **c'est le but** : ils reviennent en v2 sans travail de
conception.

Créer ces deux routes maintenant produirait deux écrans que rien n'atteint et
que `flutter analyze` neIntegrated manque pas. Le shell doit donc **ne pas** les
déclarer, et `more.md` § 3 — qui liste encore des lignes `MoreRow` `Stats` et
`Sources` — est une contradiction ouverte (§ 7, question ouverte 4).

**`/library/novel/:novelId/chapter/:chapterId` — déclarée, vide.**

Elle est dans `design-system.md` § 3.5 et dans **aucun** des dix-huit fichiers
d'écran. Chaque écran qui ouvre un chapitre pousse `/reader/:novelId/:chapterId`
(`history.md` § 3, `browse-catalogue.md` § 5, et le schéma de `library.md`). Ce
qui veut dire qu'elle est soit un résidu, soit une destination prévue dont
personne n'a écrit l'écran. Déclarer une route dont personne n'est le
propriétaire crée une destination qui mène à un `PlaceholderScreen` — pire que
son absence, parce qu'elle est joignable. **Le shell la déclare**, parce que
`design-system.md` § 3.5 est l'autorité et que la route y est écrite ; le
`PlaceholderScreen` rend un état d'interface explicite plutôt qu'une page
blanche (**B24**). La question de savoir qui possède l'écran est en § 7.

### 3.5 Le `PlaceholderScreen` — un état d'interface, pas un mensonge

C'est le seul écran que cette tranche produit, et il doit dire ce qu'il est.

```dart
// lib/app/router/placeholder_screen.dart
import 'package:flutter/material.dart';

import '../../core/ui/app_scaffold.dart';
import '../../l10n/generated/app_localizations.dart';

/// A route that exists but has no screen yet.
///
/// **Not** an empty page and **not** a spinner: B24 forbids an action that
/// fails silently to a blank screen, and this is the same failure with a
/// different address. It names the route it stands in for, so whoever opens it
/// — the owner, debugging alone (C5) — knows exactly which slice is missing.
///
/// Its copy is `commonErrorTitle` / `commonErrorBody` / `commonRetry`, three
/// keys that **already exist** in both ARB files. No new string is invented
/// for a screen that is a placeholder: it will be deleted when the real screen
/// lands, and a deleted screen that added a string leaves an orphan key.
class PlaceholderScreen extends StatelessWidget {
  const PlaceholderScreen({super.key, required this.screenKey});

  /// The path this stands in for. Shown verbatim so it can be quoted back.
  final String screenKey;

  @override
  Widget build(BuildContext context) {
    final AppLocalizations l10n = AppLocalizations.of(context);
    return AppScaffold(
      titleBar: AppBar(title: Text(l10n.appTitle)),
      content: Center(
        child: Padding(
          padding: const EdgeInsets.all(24),
          child: Column(
            mainAxisSize: MainAxisSize.min,
            children: <Widget>[
              Text(
                screenKey,
                style: Theme.of(context).textTheme.bodySmall,
                textAlign: TextAlign.center,
              ),
              const SizedBox(height: 16),
              Text(
                l10n.commonErrorTitle,
                style: Theme.of(context).textTheme.titleMedium,
                textAlign: TextAlign.center,
              ),
              const SizedBox(height: 8),
              Text(
                l10n.commonErrorBody,
                style: Theme.of(context).textTheme.bodyMedium,
                textAlign: TextAlign.center,
              ),
            ],
          ),
        ),
      ),
    );
  }
}
```

**Aucune action `Retry`** ici : il n'y a rien à réessayer, et un bouton qui ne
fait rien est un bouton menteur. `commonRetry` reste donc inutilisé par cet
écran — ce qui est correct, il est utilisé ailleurs.

### 3.6 Les quatre corrections de § 2.3 et § 2.6 — **la version livrée**

Ce que § 2.3 et § 2.6 montrent est la forme ; voici ce qui est livré, avec les
quatre défauts corrigés et comment.

**Correction 1 — `AppRouter` construit une seule fois.** Dans § 2.3,
`AppRouter.build()` est appelé **dans** `build()` de `LumenTaleApp`. Une
reconstruction de `LumenTaleApp` — et une reconstruction arrive dès qu'E12
arrive, quand le téléphone change de langue — construirait un **second**
`GoRouter`, et le premier serait perdu avec sa pile. C'est exactement la perte
d'état que E12 interdit.

```dart
// lib/app/router/app_router.dart — the router is a top-level final, built
// exactly once for the life of the process.
final GoRouter appRouter = _build();

GoRouter _build() { /* the body of § 2.3's build(), verbatim */ }
```

et dans `main.dart` : `routerConfig: appRouter`.

**Correction 2 — `AppShell` importe ses localisations.** § 2.6 utilise
`AppLocalizations` sans l'importer.

```dart
import '../../l10n/generated/app_localizations.dart';
```

**Correction 3 — un seul `Scaffold`, un seul `SafeArea`.** `AppShell` (§ 2.6)
retourne un `Scaffold` avec `bottomNavigationBar`, et chaque écran retourne un
`AppScaffold` (§ 2.5) qui est lui aussi un `Scaffold` avec son propre
`bottomNavigationBar`. Il y aurait **deux** `Scaffold` empilés et **deux**
`SafeArea`. La correction : `AppShell` n'est **pas** un `Scaffold`.

```dart
// lib/app/shell/app_shell.dart — corrected build()
  @override
  Widget build(BuildContext context) {
    // Not a Scaffold: every screen already returns an AppScaffold, which is
    // one. A Scaffold here would stack a second one and give the child two
    // SafeAreas — and the bottom nav would sit under the child's own.
    return Column(
      children: <Widget>[
        Expanded(child: navigationShell),
        _BottomNav(
          currentIndex: navigationShell.currentIndex,
          onSelected: (int index) => navigationShell.goBranch(
            index,
            initialLocation: index == navigationShell.currentIndex,
          ),
          destinations: appNavDestinations,
        ),
      ],
    );
  }
```

`_BottomNav` est un `NavigationBar` privé, construit à partir de
`appNavDestinations`. Il est **privé** parce que la barre d'onglets est
l'implémentation de `AppShell`, et qu'un `NavigationBar` public dans `app/` serait
une seconde façon de faire la même chose.

**Correction 4 — `showBottomNav` doit être faux pour `/reader/…` et
`/onboarding`.** Ces routes sont hors du shell : elles ne reçoivent pas
`AppShell` du tout, donc `AppShell` ne leur passe pas de barre. Mais
`AppScaffold` a `showBottomNav: true` par défaut, et un écran qui l'oublie
verrait une barre sous le lecteur. `design-system.md` § 2.8 règle : « `immersive`
— `readerChrome` instead of `titleBar` **and `bottomNav`** ». Le lecteur passe
donc `state: AppScaffoldState.immersive`, qui **force** `showBottomNav` à faux.
La correction est dans le `switch` de `AppScaffold.build` : l'état `immersive`
ignore `showBottomNav` et `bottomNav` entièrement, quoi qu'on lui passe.

```dart
      bottomNavigationBar: switch (state) {
        // `immersive` never shows a bottom nav, whatever was passed: the
        // reader is outside the shell (§ 3.1) and
        // `design-system.md` § 2.8 says `readerChrome` replaces
        // `titleBar` **and** `bottomNav`.
        AppScaffoldState.immersive => null,
        _ => showBottomNav && bottomNav != null
            ? Column(
                mainAxisSize: MainAxisSize.min,
                children: <Widget>[
                  if (persistentStatus != null) persistentStatus!,
                  bottomNav!,
                ],
              )
            : null,
      },
```

conservation de la pile, pas un provider.

## 5. Gestion d'état (state management)

| Donnée | Portée | Stockage | Initialisation | Mise à jour |
|---|---|---|---|---|
| Table de routes | application | `final GoRouter appRouter`, **constante de processus** | `main()`, une fois | **jamais**. Une reconstruction perdrait la pile — c'est la correction 1 de § 3.6 |
| Onglet courant | application | `StatefulNavigationShell.currentIndex` | `/library` | `goBranch` au tap |
| Pile par onglet | application | `StatefulShellRoute`, une par branche | `GoRoute` initial | `goBranch(initialLocation:)` |
| Locale active | application | `MaterialApp.locale`, résolue par `localeListResolutionCallback` | `_resolveLocale` | quand le téléphone change de langue (**E12**) |
| Thème clair / sombre | application | `MaterialApp.theme` / `darkTheme`, `themeMode` absent → `ThemeMode.system` | `_theme(...)` | quand le téléphone change (**E13**, appliqué par `theme-type`) |
| Libellé d'un onglet | par rendu | `AppLocalizations.of(context)` | à chaque `build` de `_BottomNav` | jamais mis en cache |

**Ce qui n'est pas de l'état** : l'onglet sélectionné « en dur » dans un
provider. `StatefulNavigationShell` le détient, et un second exemplaire serait
libre de diverger de la barre qui l'affiche — c'est la forme exacte du défaut que
B14 interdisait pour le compteur de non-lus.

**⚠️ La locale n'est pas de l'état applicatif.** Il n'y a **aucun** sélecteur de
langue dans l'app (**B28**) et aucune clé de prefs pour elle : la langue suit le
téléphone. `theme-type` détient `themeOverride`, qui est une **exception**
explicitement permise par **B26** (« the user may override light/dark inside the
app »), et qui n'a pas d'équivalent pour la langue.

## 7. Pièges à éviter

- **⚠️ Ne pas construire `AppRouter.build()` dans `build()`.** Le comportement
  correct (**E12**) est : un `final GoRouter appRouter` au niveau du fichier,
  construit une fois. L'appeler dans `build()` reconstruit la racine à chaque
  changement de locale et **perd la pile de navigation** — donc la position du
  lecteur. C'est le défaut le plus coûteux de cette tranche et il ne se voit pas
  au premier lancement.
- **⚠️ Ne pas utiliser `localeResolutionCallback`.** Le comportement correct
  (**B28**, **E12**) est : `localeListResolutionCallback`, qui reçoit la liste
  entière des locales préférées. `localeResolutionCallback` n'en voit que la
  première, donc `fr_CA` ne rejoint pas `fr` par code de langue et le
  fallback FR ne s'applique qu'aux cas les plus grossiers.
- **⚠️ Ne pas déplacer `_resolveLocale`.** Le comportement correct (**B28**,
  `16-i18n.md` règle 5) est : il reste dans `lib/main.dart`. C'est écrit dans la
  règle, et `architecture.md` § 3.1a dit « **keeping** the existing
  `localeListResolutionCallback` ». Le déplacer dans `app/` violerait une règle
  nommée pour un gain nul.
- **⚠️ Ne jamais mettre un rail, ni un deuxième `Scaffold`, dans `AppShell`.**
  Le rail est exclu par ADR-019 ; le deuxième `Scaffold` donnerait deux
  `SafeArea`.** Le comportement correct (ADR-019, `design-system.md` § 3.2) est :
  un `NavigationBar` de cinq éléments en bas, quel que soit l'écran ; et un seul
  `Scaffold`, celui de `AppScaffold`. Deux `Scaffold` donnent deux `SafeArea` et
  la barre finit sous la barre de l'écran.
- **⚠️ Ne pas créer `/more/sources` ni `/more/stats`.** Le comportement correct
  (`design-system.md` § 3.5, `architecture.md` § 3.1) est : ces deux routes ont
  été retirées de la v1 avec les tranches `6-9` et `6-8`, et aucune règle de la
  v1 n'en a besoin. Les créer produirait deux destinations joignables qui mènent
  à un `PlaceholderScreen` — deux écrans que le lecteur peut atteindre et qui ne
  font rien.
- **⚠️ Ne pas rendre une route inconnue par une page blanche.** Le comportement
  correct (**B24**) est : `errorBuilder` qui rend `commonErrorTitle` et
  `commonErrorBody`, plus le chemin. Les trois clés existent déjà dans les deux
  ARB.
- **⚠️ Ne pas laisser `showBottomNav` décider pour l'état `immersive`.** Le
  comportement correct (`design-system.md` § 2.8) est : `immersive` retire
  `titleBar` **et** `bottomNav`, sans condition. Le lecteur est hors du shell ;
  un écran qui passe `showBottomNav: true` par oubli doit quand même ne pas avoir
  de barre.
- **⚠️ Ne pas écrire un libellé d'onglet en littéral.** Le comportement correct
  (**B28**, `16-i18n.md` règle 1) est : `d.label(AppLocalizations.of(context))`.
  `design-system.md` § 3.2 donne les libellés dans les deux langues, et un
  litteral dans un `NavigationDestination` ne change pas de langue.
- **⚠️ Ne pas ré-ordonner les cinq destinations « pour optimiser ».** Le
  comportement correct (ADR-018) est : l'ordre vient de `state.json`'s
  `set-nav`, et il est vérifié par assertion dans les deux sens — index et
  `rank`. `Library` est premier parce qu'il a la fréquence la plus haute et
  qu'il est le seul écran qui peut **ouvrir** la boucle.

### Questions ouvertes — à trancher, pas à deviner

1. **Qui possède `/library/novel/:novelId/chapter/:chapterId` ?** Elle est dans
   `design-system.md` § 3.5 et dans **aucun** des dix-huit fichiers d'écran ;
   chaque écran qui ouvre un chapitre pousse `/reader/:novelId/:chapterId`.
   Trois lectures : un résidu à supprimer de § 3.5, une destination prévue dont
   l'écran n'a pas été écrit, ou une route distincte du lecteur pour un jour où
   la lecture serait dans la bibliothèque. **Option la moins chère et
   réversible** : la route est déclarée et rend un `PlaceholderScreen` qui
   nomme son chemin — donc elle est joignable mais pas silencieuse. Les trois
   lectures exigent toutes une modification de `design-system.md` ou
   l'écriture d'un écran, et cette tranche n'a pas le droit de faire l'une ou
   l'autre.
2. **Quelles icônes pour les cinq onglets ?** `design-system.md` § 3.2 donne
   libellés, fréquences et centralités — **pas d'icônes**. `NavigationBar` en a
   besoin. **Option la moins chère et réversible** : le jeu Material fourni
   (`conventions.md` : « Icons: Material Icons (bundled) »), une paire
   outlined / filled par destination, nommée ici. La règle du design system
   qu'elles doivent respecter est « No icon-in-a-circle as decoration » — un
   `NavigationBar` Material ne dessine aucun cercle, donc la règle est respectée
   par construction. Si le design system doit fixer les icônes, c'est une
   édition de `design-system.md` § 3.2.
3. **`navMore` n'existe pas dans les ARB.** `design-system.md` § 3.2 exige le
   libellé « More / Plus » pour la cinquième destination ; `app_fr.arb` et
   `app_en.arb` portent `navLibrary`, `navBrowse`, `navUpdates`, `navHistory`,
   `navDownloads`, `navSettings` — **et pas `navMore`**. Quatre des cinq libellés
   d'onglet existent ; le cinquième est un trou. La fondation `localisation`
   est le propriétaire des clés ARB, et elle écrit les deux fichiers dans le
   même commit (`16-i18n.md` règle 2). **Cette tranche consomme la clé, elle ne
   la crée pas** — sauf si `localisation` n'a pas été exécutée, auquel cas le
   test « chaque destination a un libellé non vide dans les deux langues » échoue
   et c'est le comportement voulu.
4. **`more.md` § 3 liste encore `Stats` et `Sources`.** Le fichier d'écran
   `more.md` § 3 énumère six `MoreRow` : `Downloads`, `Stats`, `History
   retention`, `Sources`, `Settings`, `About` — dont `Stats` et `Sources` sont
   précisément les destinations retirées de la v1 avec les tranches `6-8` et
   `6-9`. `design-system.md` § 3.5 est explicite sur leur retrait. **Les deux
   documents se contredisent**, et `0-5` ne peut pas trancher : il **n'écrit pas**
   `more.md`. Le shell ne crée pas les deux routes, et le fichier d'écran finira
   either be corrected or will describe un écran que rien n'atteint.
5. **Quatre écrans n'ont pas de tranche nommée.** `/library` (`Library`),
   `/updates` (`Updates`), `/more` (`More`) et `/browse/:sourceId/unavailable`
   (`SourceUnavailable`) sont des fichiers d'écran approuvés, et
   `architecture.md` § 3.1 ne nomme aucune tranche pour eux — `6-6` est « Unread
   badge, similar-title warning, title-only search », ce qui est une partie de
   `library.md`, pas l'écran entier ; `6-3` est « Local counting model », un
   modèle local et pas une interface ; et `source-unavailable.md` n'a **aucune**
   tranche dans l'inventaire de 35 éléments. **C'est la même famille de trou que
   la table de routes** : `architecture.md` § 3.1a dit « no slice whose job was
   to assemble them » à propos des routes, et il est vrai aussi des écrans. Le
   shell les rend joignables via `PlaceholderScreen` en attendant.
6. **Quel déclencheur de premier lancement, et où vit-il ?** E11 exige que la
   divulgation « nothing here is backed up » soit faite **au premier
   lancement**, et `3-4` porte l'écran. Mais le shell est le seul endroit qui
   pourrait rediriger vers `/onboarding` au démarrage, et le déclencheur — une
   clé de `shared_preferences` ? une colonne ? un état en base ? — **n'est
   nommé dans aucun document et n'appartient à aucune fondation**
   (`architecture.md` § 4.7 dit que `shared_preferences` porte « Reading
   settings », `theme-type` les détient, et aucun document ne mentionne un drapeau
   « vu le disclaimer »). **Option la moins chère et réversible** : **aucune
   redirection**. `/library` s'ouvre, et `3-4` décide de la forme du
   déclencheur quand il l'écrit. Le coût de cette option est qu'E11 n'est
   honoré qu'à travers `settings.md` et non au premier lancement — un écart
   réel, dont il faut qu'il soit **écrit** plutôt que passé sous silence. La
   question reste : qui possède le déclencheur, et où est-il stocké ?
7. **`test/widget_test.dart` lit `find.byType(MaterialApp)`.** Les deux tests
   existants — `configures localization for both supported locales` et
   `provides light and dark themes and honours the system mode` — font
   `tester.widget<MaterialApp>(find.byType(MaterialApp))` pour lire
   `localizationsDelegates`, `supportedLocales`, `theme` et `darkTheme`.
   `MaterialApp.router` **est** un `MaterialApp`, donc `find.byType` le trouve
   toujours et les tests devraient continuer à passer. **Mais cela n'est pas
   vérifié** et le plan ne peut pas l'affirmer sans l'avoir exécuté. Si un test
   casse, la correction est dans le test et **jamais** dans le routeur : un test
   qui force une forme de widget pour forcer une forme de widget est un test qui
   empêche la migration.
